# STX 内置监控说明

STX 自带监控：指标采集、存储、查询、趋势图和指标告警都在 STX 后端进程里完成，**不需要另外安装或维护任何监控组件**。
首页大盘、集群 / 作业趋势、作业详情的「趋势」页签、诊断报告里的指标快照和告警中心的指标告警都用这份数据。

## 采集什么

| 来源 | 内容 | 方式 |
| --- | --- | --- |
| SeaTunnel 引擎 | 每个受管集群的每个在线节点的引擎指标（JVM 堆 / 非堆、GC、线程、CPU、FD、作业线程池、Hazelcast 分区与执行器、作业状态计数等） | 后端按 `scrape_interval`（默认 15 秒）访问节点的 `seatunnel_metrics.path`（默认 `/hazelcast/rest/instance/metrics`），不需要在节点上装任何东西 |
| STX 作业 | 每个作业的读写条数 / 字节、提交条数、CDC 延迟、Checkpoint 耗时与失败次数、算子忙碌度、边背压、表级读写量 | 后端在作业状态对账时直接写入，作业结束时写入最终值后停止 |

节点不可达时，该节点在可用性图上显示为不可用，持续超时会触发「节点离线」告警。

## 配置

`config.yaml` 的 `observability` 段（默认值见 `config.example.yaml`）：

```yaml
observability:
  enabled: true              # 总开关，默认开启
  storage:
    dir: "data/tsdb"         # 数据目录，相对安装目录
    retention: ""            # 时间保留上限，默认不限（只按容量清理）；支持 s/m/h/d/w/y
    max_size: 32212254720    # 存储上限（字节），默认 30GiB；显式写 0 表示不限
  scrape_interval: "15s"     # 引擎指标采集间隔
  eval_interval: "15s"       # 指标告警评估间隔
  query_timeout: "8s"        # 单次查询超时
  max_samples: 10000000      # 单次查询最多加载的样本数（约 160MB）
  sample_limit: 50000        # 每个抓取目标单轮样本上限；超限丢弃该目标本轮
  seatunnel_metrics:
    path: "/hazelcast/rest/instance/metrics"
    probe_timeout_seconds: 2
```

修改后重启 STX 生效。

### 保留时长与磁盘

- 数据按 `retention` 与 `max_size` 两个条件删除，先到哪个按哪个。`retention` 默认不限——只按 `max_size`（30GiB）容量清理最旧块；设置了 `retention` 才再叠加时间上限。两者都不限时，启动会告警提示数据可一直涨到磁盘满。
- 查询窗口最长 366 天（首页 / 集群 / 作业趋势与作业详情趋势一致）；选更长的自定义区间会截取最近一年并给出提示。
- 长窗口的「读写量」按周 / 月分桶，早于最早样本的整桶标记为 `no_data`（不计为 0）；跨最早样本的桶标记 `partial`。
- 想限制保留时长，设置 `retention`（如 `90d`）；想给更大磁盘，调大 `max_size`。
- 占用大致与「节点数 × 引擎指标数 + 作业数」成正比，几十个节点的规模通常在几 GB 以内。
- 内嵌 tsdb 自己的 `prometheus_tsdb_*` / `prometheus_engine_*` 以及 STX 进程的 `go_*` / `process_*` 会以 `job="stx_embedded"` 写回同一存储，可用 `stx monitoring integration status` 看 `embedded_tsdb.meta`（head 序列、块字节、compaction 失败次数）。
- 每个抓取目标单轮超过 `sample_limit`（默认 5 万样本）时，只丢弃该目标本轮并在状态接口记 `last_error`，不影响其他节点。建议活跃序列不超过 2 万；详见 `.trellis/spec/backend/embedded-tsdb-capacity.md`。
- 容量数字分两档：突发写入（`go test` 三档序列）和实时长时间运行。后者按 15s 抓取至少跑 48h：`./scripts/tsdb-soak.sh`（输出 `tmp/tsdb-soak-48h.jsonl`）。突发档不能代替 48h soak。

## 告警

STX 的告警在 `/monitoring`（告警中心）统一管理，分三个面板：**告警**（实例列表与处理）、
**规则**（集群级规则目录与作业级规则）、**通知**（默认通知、通知渠道与投递记录）。

### 告警范围

- 告警中心按**范围**（`scope`）过滤，取值 `cluster`（集群级）与 `job`（作业级）：
  集群级规则覆盖平台健康与集群指标（节点离线、CPU 高等）；作业级规则按任务配置生效（作业运行失败、CDC 延迟过高等）。
- `source_type` 只表达内部来源类别（`platform_health` / `metric` / `job`），列表展示统一用 `scope`；
  需要区分 sync 阶段时按 `alert_id` 的 `sync:` 前缀判断（例如阶段专属的发生次数、自动关闭原因展示）。
- 巡检自动策略的「告警触发」条件从 `GET /api/v1/monitoring/alert-rules/catalog` 选择规则键精确匹配，
  可叠加「至少 N 个对象同时触发」与「至少持续 N 分钟」。

### 集群级规则目录

集群级规则是一份**内置目录**（21 条）：规则本身不能新增或删除，只能在全局层或单个集群上修改
开关、阈值、持续时间、级别与通知方式（规则页 → 集群级）：

| 规则键 | 名称 | 默认 | 阈值 / 持续时间 |
| --- | --- | --- | --- |
| `node_offline` | 节点离线 | 开 | 节点进程停止、缺失或引擎指标不可达 / 2 分钟（Agent 心跳超时归 `agent_offline`） |
| `master_unavailable` | Master 不可用 | 开 | 无阈值 / 1 分钟 |
| `worker_insufficient` | 可用 Worker 不足 | 开 | 健康 Worker < N（默认 N = 部署 Worker 数，可改固定值）/ 2 分钟 |
| `agent_offline` | Agent 离线 | 开 | 无阈值 / 2 分钟 |
| `process_crashed` | 进程崩溃 | 开 | 事件即时触发 |
| `process_restart_failed` | 进程重启失败 | 开 | 事件即时触发 |
| `process_restart_limit_reached` | 达到重启上限 | 开 | 事件即时触发 |
| `sync_status_unavailable` | 作业状态获取失败 | 开 | 无阈值 / 5 分钟 |
| `split_brain_risk` | 分区不安全 | 开 | Hazelcast 分区安全检查异常 / 2 分钟 |
| `deadlocked_threads_detected` | 线程死锁 | 开 | > 0 / 1 分钟 |
| `job_thread_pool_rejection_high` | 任务被拒绝 | 开 | 拒绝率 > 0 / 5 分钟 |
| `memory_usage_high` | JVM 堆内存高 | 开 | > 85% / 10 分钟 |
| `fd_usage_high` | FD 使用率高 | 开 | > 80% / 10 分钟 |
| `cpu_usage_high` | CPU 高 | 关 | > 80% / 10 分钟 |
| `gc_time_high` | GC 耗时高 | 关 | > 20% / 10 分钟 |
| `job_thread_pool_queue_backlog_high` | 线程池队列积压 | 关 | > 100 / 5 分钟 |
| `coordinator_backlog_growing` | 积压持续增长 | 关 | 队列 > 50 且提交速率持续高于完成 / 10 分钟 |
| `failed_jobs_high` | 失败作业数过高 | 关 | > 0 / 1 分钟 |
| `sync_event_channel_degraded` | 作业事件通道降级 | 关 | 事件即时触发 |
| `cluster_restart_requested` | 集群重启请求 | 关 | 事件即时触发 |
| `node_stop_requested` | 节点停止请求 | 关 | 事件即时触发 |

- **阈值单位**：百分比规则一律显示为 `> 85%` 形式；`worker_insufficient` 的阈值默认「等于部署
  Worker 数」，可改为固定值；无阈值规则（进程事件类）只有持续时间。
- **持续时间**表示条件连续成立多久才触发；事件类规则即时触发。
- **级别语义**：`warning`（警告）只进入告警中心，不发送外部通知；`critical`（严重）必须外发——
  保存为严重时，生效通知里至少要有一条启用的渠道，否则保存被拒绝。
- **通知层级**：默认通知（通知面板）→ 规则的「自定义」通知 → 集群例外的自定义；每层也可以选
  「不通知」。不再区分通知路由。
- **集群例外**：在规则详情里为单个集群覆盖开关 / 阈值 / 持续时间 / 级别 / 通知；例外只存与全局
  不同的字段，删除例外即回到全局配置。
- **作业级规则**：在每个任务的告警设置里配置（任务侧栏或规则页「作业级」面板），规则、阈值与
  通知渠道按任务生效，接口仍为 `sync_job` 类型的告警策略。

集群规则与默认通知也可以用 `stx` CLI 管理（写操作需要 `--confirm`，请求体用 `--request-file` 传入，
响应里返回一次性确认要求时把 `confirmation_id` 用 `--confirmation-id` 带上重试）：

```bash
stx monitoring cluster-rule list                          # 集群级规则目录与生效配置
stx monitoring cluster-rule get node_offline              # 单条规则的目录默认 + 全局配置 + 集群例外
stx monitoring cluster-rule update node_offline --request-file ./rule.json --confirm
stx monitoring cluster-rule override set node_offline 6 --request-file ./override.json --confirm
# 删除例外（回到全局配置）：CLI 暂不提供 delete，用接口 DELETE /api/v1/monitoring/cluster-rules/node_offline/clusters/6
stx monitoring notification-defaults get                  # 默认通知（渠道、接收人、冷却）
stx monitoring notification-defaults update --request-file ./defaults.json --confirm
```

告警的去重、冷却重发、静默、恢复通知与确认处理统一由告警中心承担；处于告警中的阶段跨重启保留，
恢复通知照常发送。

## 从旧版本升级

旧版本通过外部的 Prometheus / Alertmanager / Grafana 提供监控。升级到内置监控有两种方式，后续行为不同：

### `install.sh` 重装升级

重新运行 `install-online.sh`（同目录覆盖安装）会用**当前安装脚本**直接写入新的 `bin/` 全套脚本，不经过旧升级器，升级后不需要任何布局修复。
旧的 `observability/` 目录和数据**保留不删**，确认不需要后可手动删除。

### 应用内一键升级（界面 / API / CLI）

一键升级由**旧版本升级器**执行，它只替换 `stx` 二进制、`lib/`、`scripts/` 和 `frontend/`，**不会替换 `bin/`**。
因此修复动作放在新二进制启动流程里，首次启动时自动完成：

- **安装布局自修复**：检测到安装目录布局时，用内嵌的新脚本覆盖 `bin/start.sh` / `bin/stop.sh` / `bin/status.sh`
  （旧文件备份为 `bin/<名>.bak-<UTC 时间戳>`），并把 `bin/lib/observability.sh` 移走为 `.bak-<时间戳>`；幂等，第二次启动不再重复。
- **旧三件套收尾**：启动后约 3 分钟窗口内按 `observability/*/*.pid` 文件逐个停止仍在运行的 Prometheus /
  Alertmanager / Grafana（发信号前用 `/proc/<pid>/exe` 核对进程身份，pid 被复用时只清理 pid 文件）。
  `observability/` 数据目录保留不删。
- **遗留告警收尾**：外部 Alertmanager 时代产生、从未恢复的告警会被一次性标记为已恢复，不发送恢复通知。
- **失效配置提示**：旧条件（`PROM_*` / `NODE_UNHEALTHY`、未选规则的 `ALERT_FIRING`）的自动巡检策略不再生效但不会被删除；
  列表 / 详情 API、CLI 与诊断面板会通过 `invalid_reason` 原因码
  （`legacy_source_type` / `legacy_condition_code` / `alert_firing_without_rule_keys`，
  另附 `invalid_detail` 携带具体失效取值）标出，需编辑重新选择。
- **告警配置一次性迁移**：升级后首次启动把旧的指标模板 / 平台健康策略迁移为集群规则的全局配置与
  集群例外（SchemaFlag `alert_rule_catalog_v1`，事务内执行，重复启动不再跑）；旧通知路由按过滤条件并入
  默认通知或对应规则的自定义通知；有启用渠道的策略记为严重级别、无渠道的记为警告。旧策略行保留但置为
  停用，便于排查；`sync_job` 任务告警策略不受影响。

升级后 `bin/start.sh` 不再启动任何外部监控组件；如果还在用旧 systemd 单元，其传入的 `--observability`
参数会被接受并忽略。

#### CLI 一键升级

除界面外，升级全流程也可以用 `stx` CLI 完成（离线环境用本地升级包，无需访问 release 地址）：

```bash
stx auth login --server http://127.0.0.1:17800 --username admin --password-stdin

# 在线升级：下载 release 资产后执行
stx self-upgrade stage --target-version vX.Y.Z
# 或离线升级：导入本地升级包（流式上传，不会把包读进 CLI 内存）
stx self-upgrade import ./stx-upgrade-X.Y.Z.tar.gz --confirm

stx self-upgrade execute          # 真实执行；--dry-run 只演练
stx self-upgrade task get <id> --wait --timeout 6m   # 等待任务到终态，控制面重启瞬断会自动重试
stx self-upgrade task cancel <id> --confirm          # 取消仍可取消的任务
```

`import` / `task cancel` 属于影响写操作，需要 `--confirm`；服务端返回一次性确认要求时，把响应里的
`confirmation_id` 用 `--confirmation-id` 带上重试即可。

### 一键升级回滚后的恢复

一键升级的回滚由**旧版本升级器**执行：它只还原旧二进制，不会还原 `bin/` 脚本，也不会把已停掉的
旧三件套拉回来。回滚后旧版本跑的是新 `bin/start.sh`（不启动外部监控），且 `bin/lib/observability.sh`
已被移走——即旧版本监控整体失效。

如需在回滚后恢复旧监控三件套，手工把备份改回原名再重启：

```bash
cd /opt/stx/bin
for f in start.sh stop.sh status.sh; do
  mv "${f}.bak-"* "$f" 2>/dev/null   # 多个备份时先确认时间戳再 mv
done
mv lib/observability.sh.bak-* lib/observability.sh
systemctl restart stx
```

（`bin/` 里可能有多个 `.bak-<UTC 时间戳>` 文件，恢复前先看时间戳选对一份。）

### 删除的接口

以下接口已随外部监控栈移除，调用方会收到 404：

- `GET /monitoring/prometheus/discovery`
- `GET /monitoring/prometheus/jobs/metrics`
- `POST /monitoring/alertmanager/webhook`（外部 Alertmanager 推送端点，请停止推送）
- `ANY /monitoring/proxy/grafana`
- `ANY /monitoring/proxy/grafana/*proxyPath`

STX 对外推送告警通知的 webhook / 飞书 / 企业微信 / 钉钉 / 邮件渠道不受影响。

### 其他升级注意事项

- 内置监控**默认开启**：默认不限保存时长、按容量保留（`observability.storage.max_size`，示例配置缺省时自适应为 min(30 GiB, 磁盘 20%)）；需要限时可用 `observability.storage.retention` 设上限。
- 内存 / 磁盘占用相比旧三件套整体下降，但新增了内置 tsdb 的常驻开销：小内存机器（< 2 GiB）建议调低
  `observability.storage.max_size` 与 `sample_limit` 等容量 / 采集上限。
- **时区变化**：引擎时间回退从「展示时区」改为控制面机器时区（`time.Local`）。升级前建议把各 Agent
  所在机器的时区与控制面对齐；容器部署建议显式设置 `TZ` 或 `STX_SEATUNNEL_TIMEZONE`。
- **Agent**：老版本 Agent 继续兼容，但主机指标采集与节点时区上报需要把 Agent 升级到当前版本才会完整工作。
- 旧配置文件里的 `observability.prometheus` / `alertmanager` / `grafana` / `remote_ingest` 段会被忽略，
  不影响启动，加载时记一条 WARN 提示清理。
- 旧的安装参数（`--with-observability`、`--prometheus-port`、`--alertmanager-port`、`--grafana-port`）
  不再被接受，传入会报 unknown option，请从安装命令里移除。
- **Docker Compose**：升级到只剩 STX 前后端与数据库容器后，用 `docker compose up -d --remove-orphans`
  移除遗留的 Prometheus / Alertmanager / Grafana 容器；监控数据在 `data/stx/tsdb`。
- 历史监控数据不自动迁移，升级后从零开始积累。若必须查看旧数据，可把 `storage.dir` 临时指向旧的
  Prometheus 数据目录（同为同一存储格式）。

## 常见问题

**趋势图显示「监控数据暂不可用」**：数据目录无法打开（权限、磁盘满）或查询超时。查看 `logs/backend.log` 中 `[Observability]` 开头的日志。

**某个节点的图是空的**：确认节点在线、配置了 Hazelcast 端口，且 STX 能访问 `http://<节点 IP>:<Hazelcast 端口><seatunnel_metrics.path>`。

**作业趋势没有数据**：作业趋势来自作业状态对账，作业需要处于运行中；已结束的作业可以在作业详情里按「作业全程」查看历史。
