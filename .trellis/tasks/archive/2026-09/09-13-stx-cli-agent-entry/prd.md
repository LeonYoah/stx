# 设计 STX CLI AI Agent 入口

## 目标

为 STX 增加可直接执行的 `stx` CLI，使无法直连生产 SeaTunnel 服务器的 AI Agent 能通过 STX 远端 API，在受控、安全且结果稳定的接口上收集排障证据、执行测试并协助升级验证。

CLI 不只是现有前端接口的命令行外壳。它面向 AI Agent 和自动化脚本，需要提供容易发现、容易组合、可限制风险、便于机器解析的命令约定，并将常用排查步骤收进 STX 服务端能力中，减少 AI 直接操作生产服务器和 SeaTunnel 进程的需要。

## CLI 与诊断中心的关系（已确认）

- `stx` CLI 是调用入口，不另做一套诊断引擎。调用路径是 `stx CLI -> STX API -> 诊断中心 -> stx-agent 或 STX 内部数据源`。
- 诊断中心负责登记可执行的诊断资源及其命令。每项资源都有稳定编码、用途、参数、执行位置、风险等级、性能影响、超时、结果类型和审计规则。
- 每项诊断资源既能被单独执行，也能被一键诊断包选中后组合执行。只需要部分证据时，CLI 或网页可以只运行对应资源，不强制生成完整诊断包。
- 一键诊断包不再依赖一套单独的采集实现，而是编排用户勾选的诊断资源。生成 Manifest、渲染 HTML 和标记完成属于内部流程，不作为可单独采集的资源公开。
- 单项执行和诊断包执行使用同一个资源执行器、参数校验、权限判断、结果格式和审计记录，避免两种入口产生不同结果。
- 每次单项资源执行都先在诊断中心创建持久化执行记录并分配执行编号，包括能够很快完成的查询。执行记录保存资源编码、参数摘要、调用者、目标、状态、产物和关联请求编号。
- CLI 执行单项资源时默认等待任务结束，并返回最终资源元数据或下载信息；调用者可以使用 `--detach` 不等待结果，立即取得执行编号，之后再查询状态或等待完成。
- 诊断中心的资源登记是诊断命令的定义来源；平台总操作登记表引用诊断资源编码，用于生成 CLI 命令、OpenAPI、帮助和覆盖检查，不再复制维护另一份诊断命令说明。
- 命令树、登录令牌、命名空间、输出格式和客户端兼容检查仍属于 CLI 自身设计；权限、确认、幂等和审计由服务端执行，因此网页、CLI 与其他 API 客户端遵守相同规则。

## 首批诊断资源（已确认）

- `error-context`：错误组、错误事件和巡检来源。
- `process-events`：进程启停、异常退出和自动拉起记录。
- `alerts`：告警快照。
- `metrics`：CPU、内存、GC、线程和集群安全状态等指标。
- `deployment`：集群版本、部署模式、节点、角色和运行状态。
- `configs`：SeaTunnel、Hazelcast、JVM 和日志等配置，返回前脱敏。
- `jar-inventory`：`lib`、`connectors`、`plugins` 中的 JAR 和依赖信息。
- `logs`：按节点、任务和时间范围采集日志片段。
- `task-history`：任务定义、版本、提交记录和历史实例，秘密字段脱敏。
- `job-runtime`：运行状态、作业日志和 Checkpoint。
- `system-env`：经过筛选和脱敏的系统及进程环境信息。
- `thread-dump`：线程栈。
- `class-histogram`：JVM 类直方图。
- `heap-dump`：JVM 堆转储。
- `seatunnel-source`：对应版本源码包的元数据和下载入口。

## 目标用户与场景

- 主要用户是通过 Shell 调用工具的 AI Agent。
- 次要用户是需要在终端中排查 SeaTunnel 问题的开发者和运维人员。
- AI Agent 可以访问 STX API 地址，但可能无法 SSH 登录 SeaTunnel 节点，也可能无法直连 SeaTunnel 服务端口。
- 用户先登录远端 STX，再通过 `stx` 命令读取排障信息或发起受控操作。
- 查询结果应能直接作为 AI Agent 的证据，避免依赖网页解析或人工复制。

## 已确认要求

- STX 使用 Go，实现出的程序可以直接作为命令执行。
- 同一个 `stx` 二进制既可以启动 STX API 服务，也可以作为连接远端 STX 的客户端；STX 的调度、巡检和后台维护逻辑由 API 进程内部启动，不再提供独立 Scheduler 或 Worker 服务。
- `stx-agent` 与 `stx` 保持两个独立二进制。Agent 继续保持轻量，只负责节点注册、心跳、受控命令和文件传输，不加入 STX 控制端 CLI 或 API Server 代码。
- 服务端正式入口采用 `stx server`。直接执行 `stx` 时只显示帮助，不启动服务，也不初始化数据库。
- 旧的 `stx api` 作为隐藏且标记废弃的兼容入口保留一个版本，行为等同于 `stx server`，之后移除。遗留的 `stx scheduler`、`stx worker` 不再作为公开命令提供。
- CLI 直连用户指定的远端 STX API 服务地址。
- CLI 支持登录，并在后续请求中携带自己的认证信息。
- CLI 请求固定使用 `Authorization: Bearer <token>`、`X-STX-Client: cli` 和 `User-Agent: stx-cli/<version>`。服务端据此识别直接 CLI 调用；不增加单独的协议版本 Header，API 主版本继续由 `/api/v1` 表示。
- STX 为查询和诊断能力提供经过安全限制的命令入口，尽量避免 AI 直接操作生产服务器或影响 SeaTunnel。
- 命令应包含常见排查步骤，使 AI 获取的信息更准确、更集中。
- 候选能力包括：日志、集群指标、任务提交记录、任务历史、集群部署情况、配置文件、系统变量、JAR 包信息、SeaTunnel 源码、线程快照、直方图和 dump。
- 候选操作包括：代替用户提交或运行测试任务，以及执行 STX/SeaTunnel 升级测试。
- 查询类和操作类能力必须有清楚的风险边界；不能因为 CLI 面向 AI 就默认授予服务器任意操作权限。
- 首个版本覆盖 STX 平台的全部现有接口。可直接复用的 HTTP API 应转换为对应 CLI 命令，而不是只选择少量只读接口。
- 所有现有接口都需要进入一份覆盖清单，明确对应的 CLI 命令、请求方法、权限、风险等级、输出方式和测试状态，防止新增 API 后 CLI 长期缺失。
- POST、PUT、PATCH、DELETE 以及其他可能改变状态的接口，需要按实际影响决定是否二次确认，并考虑重复调用保护。
- CLI 帮助必须说明命令会访问哪些 STX 或 Agent 能力、是否在服务器执行预设命令、是否改变状态、可能产生的性能影响，以及结果保存在哪里。
- STX 可以通过现有 Agent 通道补充服务器信息采集能力，但服务器侧只能执行提前定义、可查看、经过参数限制的命令，不提供任意 Shell。
- 诊断中心的一键诊断包继续保留；诊断包中的资源必须登记为可单独执行的查询或采集命令，支持 AI 按需实时获取和分析。一键诊断包通过勾选这些资源进行组合。
- 审计功能需要扩充，覆盖 CLI 请求、普通 API 请求、诊断资源采集、Agent 命令和有状态操作，而不再只记录部分业务操作。
- CLI 使用独立于浏览器 Cookie 的会话令牌。`stx login` 使用现有用户名和密码换取随机令牌，后续请求通过 `Authorization: Bearer <token>` 发送。
- 服务端数据库只保存 CLI 令牌哈希及其元数据；令牌必须支持过期、列出和撤销。令牌不保存独立权限范围，也不保存签发时的权限快照，始终使用所属用户的当前权限。
- 服务端处理每次 CLI 请求时都查询所属用户的当前状态和权限。用户被禁用、删除或权限发生变化后，已有 CLI 令牌立即按新状态处理，不需要逐个修改或重新签发令牌。
- 后续即使用户权限从管理员标记扩展为更完整的权限模型，令牌仍只负责证明调用者身份，不另建一套令牌权限配置。
- 浏览器继续使用现有 Cookie 会话。`X-STX-Client` 和 `User-Agent` 只用于来源识别、日志与审计，不作为认证凭据，也不能提高权限；服务端应分别记录认证方式、客户端类型和客户端版本，不能仅凭可伪造的 Header 判断调用身份。
- 审计记录用户、CLI 令牌编号和 CLI 版本，不记录令牌原文。
- 普通用户只能查看自己发起或归属于自己的 API、CLI、Agent、诊断和任务执行审计记录；管理员可以按权限查看全部记录。
- 系统自动执行的审计记录默认只允许管理员查看；如果系统执行明确关联某个用户拥有的任务或执行，该用户可以查看与该任务或执行相关的记录。
- 审计事件采用只追加方式保存，不提供修改或按条删除的产品接口。命令执行记录可以随真实执行进展更新状态，但每次重要状态变化都要留下对应的不可修改审计事件。
- 审计过期数据只能由服务端按保留策略清理，并为清理操作本身留下记录。首版不提供审计导出 API 或 CLI 命令，只提供受权限限制的分页查询和详情查看。
- 每项 CLI/API 操作按实际行为登记风险等级，不按 GET、POST、PUT、DELETE 等 HTTP 方法直接判断。
- R0 为普通查询，不需要确认。
- R1 为低影响写入，例如创建草稿或修改说明。CLI 使用布尔型 `--confirm` 和幂等键执行；非交互环境未提供 `--confirm` 时只返回预览或确认要求，不改变远端状态。
- R2 为会影响任务或服务的操作，例如提交任务、安装插件、采集线程快照或重启节点。服务端第一次请求只返回结构化影响说明和短期确认编号，不执行操作；第二次请求必须通过 `--confirmation-id <id>` 携带确认编号后才执行。
- R3 为删除资源、停止集群、执行升级、JVM Dump、清理运行存储等高风险或高负载操作；除 R2 规则外还要求管理员权限，且不能通过通用 `--yes` 参数或仅使用布尔型 `--confirm` 跳过服务端确认。
- R2、R3 的确认编号必须是单次使用、短期有效，并绑定用户、CLI 令牌、操作、目标和请求参数；任一内容改变都必须重新申请确认。
- TTY 环境可以在显示影响说明后询问用户；用户确认后，CLI 可以自动完成 R1 执行或 R2、R3 的第二次请求。非 TTY 环境永不弹出交互提示，AI Agent 和脚本必须显式提供 `--confirm` 或 `--confirmation-id`。
- R1、R2、R3 统一使用服务端幂等记录。CLI 默认生成 `Idempotency-Key`，同时允许调用者通过 `--idempotency-key <key>` 明确指定；服务端以“用户、`operation_id`、幂等键”查找记录，并保存规范化请求的摘要。
- 同一幂等键和相同请求在执行中时返回原执行编号与当前状态，执行结束后返回原结果或结果引用，不再次执行；同一幂等键对应不同请求时返回 HTTP 409 和稳定错误码 `idempotency_conflict`。
- R2、R3 从申请确认编号开始就使用同一个幂等键，确认编号同时绑定该键。CLI 自动重试必须复用原键，不能因网络超时生成新键。运行中的幂等记录不清理，执行结束后保留 24 小时；审计记录仍按审计保留规则保存。
- 可修改资源的查询结果返回资源 `revision`，并可通过 HTTP `ETag` 表达同一版本。CLI 对更新、删除以及依赖该资源当前状态的执行操作提供 `--revision <n>`，向服务端发送 `If-Match`；如果命令基于刚读取的对象生成修改，CLI 可以自动携带已读取的版本。
- 服务端发现资源版本已经变化时返回 HTTP 409 和稳定错误码 `revision_conflict`，不得执行目标操作。调用者需要重新查询资源，再次检查变更内容；R2、R3 还需要重新申请确认编号。确认编号必须绑定资源版本，防止预览后资源发生变化仍继续执行。
- 能力查询中 `operations[].revision` 表示操作协议修订号，资源响应中的 `revision` 表示资源当前版本，两者用途不同。首版不强制现有网页调用同时改用条件请求；没有可靠资源版本的旧接口必须在操作登记表中说明限制，并决定是否允许 CLI 调用。
- 各模块继续维护自己的任务、步骤和业务结果，不强制改成一张通用任务表。安装、升级、诊断、同步等过程不同，公共部分只负责提供一致的执行编号、状态、等待、取消、审计和结果引用。
- 所有向 CLI 暴露的异步操作都返回稳定的 `execution_id`。CLI 提供 `stx execution get`、`stx execution wait` 和 `stx execution cancel`，服务端将公共执行记录映射到各模块原有任务记录。
- 每条公共执行记录都保存稳定的 `owner_user_id`。执行归属以用户为准，与发起时使用的 CLI 令牌、命名空间、机器和客户端类型无关。
- 同一用户可以使用自己的任意有效登录方式查询、等待或取消自己的执行；服务端每次仍按该用户当前状态和权限检查。令牌编号、命名空间、机器信息和客户端版本只用于审计，不决定执行归属。
- 普通用户不能管理其他用户的执行；管理员可以按权限查看和管理全部执行。系统自动创建的执行使用明确的系统发起类型，不伪装成某个普通用户。
- 公共执行状态至少包含 `pending`、`running`、`cancel_requested`、`cancelling`、`cancelled`、`succeeded`、`failed` 和 `timed_out`。模块可以保留更详细的内部状态，但必须稳定映射到公共状态。
- 收到取消请求后，服务端先原子地记录 `cancel_requested`，再把请求传到实际执行者。只有后台任务、SeaTunnel 作业、Agent 命令或本地进程已经停止并得到确认后，状态才能变为 `cancelled`。
- 执行记录必须返回 `cancellable`。当前阶段不能安全停止时返回 `cancellable: false` 和稳定原因；请求到达过晚时返回 `too_late_to_cancel` 及当前真实状态，不能只改数据库状态来表示取消成功。
- 取消本身是幂等操作。重复取消同一执行不会重复发送有副作用的停止命令；并发完成与取消必须通过受控状态迁移处理，终态不能被迟到的后台结果随意覆盖。
- 安装、升级、Dump 等需要清理或恢复的操作，在取消结果中说明已经停止到哪个阶段、是否执行清理或恢复及其结果。清理或恢复未完成前不能宣称整个取消流程已经完成。
- 首版做不到真实取消的模块要明确标为不可取消；现有“只改状态”的取消入口必须修正或停止向 CLI 提供，不能继续返回看似成功的取消结果。
- `execution get` 和 `execution wait` 是 R0 查询，不需要确认。
- 取消普通文件下载、停止不会改变目标服务状态的证据采集属于 R1，使用布尔型 `--confirm` 和幂等键。
- 停止 SeaTunnel 作业或会影响目标服务的普通 Agent 操作属于 R2，需要服务端签发确认编号。
- 中断安装、升级、回滚等可能留下不完整状态的操作属于 R3，需要管理员权限和服务端签发确认编号。
- 取消操作按自身影响登记风险，不直接照搬原始操作的风险等级。当前阶段不能安全停止时返回 `cancellable: false`，不进入确认流程。
- 调试工作台任务定义以 `owner_user_id` 归属用户。新建任务默认私有，所有者可以显式改为共享。
- 私有任务只有所有者和管理员可以查看、编辑、删除、发布和运行。共享任务允许具备工作台使用权限的用户查看和运行，但只有所有者和管理员可以编辑、删除、发布、修改共享范围和修改调度配置。
- 任务版本继承任务定义的访问规则，不能通过版本列表、版本详情或版本回退绕过任务权限。
- 预览、提交和恢复产生的执行归实际发起用户所有。共享任务只共享定义，不自动共享运行历史；普通用户只能查看和管理自己的执行，管理员可以按权限查看和管理全部执行。
- 服务尚未部署，调试工作台直接采用新的所有者和共享规则，不设计旧任务迁移、默认所有者推断或兼容旧权限行为的临时分支。
- 工作台全局变量也按用户归属管理。变量默认私有，所有者可以显式设为共享；私有变量只能被所有者的任务和管理员任务引用，共享变量允许有工作台使用权限的其他用户任务引用。
- 全局变量的修改、删除和共享范围变更只允许变量所有者或管理员执行。变量列表和详情遵循访问范围，秘密变量始终只返回掩码，任何用户和管理员都不能通过 API、CLI、日志或任务结果取回明文。
- 任务运行时只能加载当前任务有权引用的变量；不能因为变量名称是全局唯一就自动获得其他用户私有变量的使用权。变量引用、使用者和任务需要写入审计，但审计不得保存变量原值。
- 除 `heap-dump` 外，诊断命令首版不增加专用的调用频率或冷却时间。普通任务队列容量、超时、输出大小、权限、风险确认、幂等和审计规则仍然有效。
- `heap-dump` 按单个 JVM 限制，每个 JVM 10 分钟内最多开始一次，其他节点或 JVM 不受该间隔影响。间隔从实际开始采集的时间计算；间隔内的重复请求不执行，并返回稳定错误码、剩余等待秒数和下次允许时间。
- `heap-dump` 的限制对象至少由集群、节点、PID 和 JVM 启动时间共同识别。JVM 重启后视为新的进程，不能只用可能被系统重复分配的 PID 判断。
- 同一个 JVM 同一时间只能执行一个 `thread-dump`、`class-histogram` 或 `heap-dump`。不同 JVM 可以并行执行，互不占用彼此的执行位置。
- 目标 JVM 已有诊断命令运行时，新请求不进入等待队列，也不调用 Agent，直接返回稳定错误码 `target_busy`、当前 `execution_id`、资源类型及用于查询或等待现有执行的 `next_command`。
- 因 `target_busy` 被拒绝的请求不算实际开始，不触发 `heap-dump` 的十分钟限制。互斥目标同样使用集群、节点、PID 和 JVM 启动时间识别，防止 PID 重用造成误判。
- 线程快照、类直方图和 Heap Dump 在尚未发送给 Agent 时都允许取消。取消后不得再发送原命令，并释放目标 JVM 的互斥占用。
- 线程快照和类直方图已经开始后仍允许请求取消。控制端必须把取消传给 Agent，由 Agent 终止对应工具进程并清理未完成的临时产物；只有 Agent 确认工具进程已经停止后，公共执行状态才能变为 `cancelled`。
- Heap Dump 一旦在 Agent 上实际开始，执行记录立即返回 `cancellable: false`，稳定原因是 `heap_dump_already_started`。终止本地 `jcmd` 或 `jmap` 客户端不能证明目标 JVM 内部的 Dump 已停止，因此不能把它报告为取消成功。
- 取消到达时诊断命令已经完成，返回 `too_late_to_cancel` 和真实终态。Agent 离线或无法确认工具进程已经停止时，执行保持 `cancelling`，最终按取消超时或取消失败处理，不能写成 `cancelled`。
- 自动诊断策略中的线程快照、类直方图和 Heap Dump 默认均不执行。创建或修改策略时可以分别勾选需要自动执行的 JVM 诊断资源，未勾选的资源不能被自动策略临时追加。
- 自动策略中的 Heap Dump 选项只有管理员可以勾选、保存和启用。线程快照和类直方图不增加专门的管理员限制或持续授权模型，按自动策略本身的普通配置权限处理。
- 自动策略触发的 JVM 诊断仍使用相同的目标互斥、Heap Dump 十分钟限制、影响说明、产物保存、审计和真实取消规则，不能因调用来源是系统任务而放宽限制。
- 被登记为可能影响目标进程、节点或集群的诊断命令，确认预览和最终执行结果都必须带有 `impact`。该字段至少包含稳定 `code`、影响级别 `level`、`may_affect_cluster`、影响范围 `scope`、可读 `message` 和可能出现的现象 `possible_effects`。
- `impact` 不是只给网页或人工看的提示。默认 JSON、`table`、`yaml` 以及失败响应都要保留或显示该信息，AI Agent 不读取 `help` 也能判断风险。
- `heap-dump` 的影响说明必须明确提示：操作可能请求 Full GC、暂停目标 JVM，并占用较多磁盘空间和磁盘 I/O，可能影响该节点上的任务和集群运行。线程栈与直方图返回各自登记的影响说明。
- 首版不新增不会修改集群的模拟升级模式。“升级测试”复用现有升级预检查和真实升级流程：预检查用于发现安装包、插件、节点和运行条件问题，但不能宣称真实升级一定成功。
- 真实升级必须明确指定目标集群和目标版本，按 R3 操作处理，要求管理员权限、结构化影响说明和二次确认；执行时继续使用现有冒烟测试与失败回滚步骤。
- 首版不新增“AI 测试任务”类型。AI Agent 和人工用户共用现有任务配置校验、连接测试、数据预览和真实提交能力，也共用任务实例、状态、日志、Checkpoint 和取消接口。
- 配置校验和连接测试使用现有查询检查结果；数据预览继续使用现有 `RunTypePreview`、行数限制和超时限制，并返回运行目标及影响说明；真实提交按 R2 操作处理，必须明确目标集群、通过二次确认并携带幂等键。
- AI 发起的预览和任务提交不另建任务表或执行模型，通过请求来源、CLI 令牌编号、用户、请求编号和审计记录识别。
- 安装包管理下载流程新增“同时下载源码”选项，默认选中。下载 SeaTunnel 运行包时，STX 同时下载同版本源码包并建立关联，供 AI Agent 分析故障。
- 安装包导入页面支持同时选择两个文件：运行包为必需，源码包为可选。两个文件分别上传和处理；运行包成功后立即进入本地安装包列表，不等待源码包。源码包必须与运行包版本一致，不能被当作运行包安装到集群节点。
- 安装包及其关联源码需要通过平台 API 和 CLI 查询状态。首版只提供源码包下载，AI Agent 下载到本地后自行解压和分析；STX 服务端不提供源码文件浏览、检索或内容读取。
- 本地安装包列表以运行包是否存在为准。列表新增源码列，显示未导入、处理中、已导入或失败等状态；运行包导入或下载成功后立即显示该行。
- 自动下载源码失败不影响运行包成功。运行包下载完成后仍可用于安装和升级；源码列记录失败状态、原因和重试入口。
- 已有运行包但没有源码时，用户可以按版本从网络自动导入源码，也可以单独手工上传源码。源码的补充、重试和替换不改变运行包状态。
- 首版资源类能力采用“元数据查询 + 文件下载”：API/CLI 返回资源名称、类型、大小、校验值、生成或导入时间及下载入口，不在 STX 服务端解析资源内容。该约定适用于源码包以及其他需要以文件交付的大型资源。
- 节点生成的 Heap Dump、大型日志归档等文件由 Agent 保存，STX 控制端只保存产物编号、所属执行、目标、类型、大小、SHA-256、生成时间、过期时间和状态，不在控制端长期保存文件副本。
- 客户端下载节点产物时只能提交诊断中心签发的产物编号，不能传入 Agent 上的任意文件路径。STX 完成权限检查后触发 Agent 分块读取，并把数据实时中转给 CLI。
- 节点产物下载支持偏移续传、长度和 SHA-256 校验。CLI 先写临时文件，全部校验通过后再改为目标文件名；连接中断后可以从已确认的偏移继续。
- 下载节点产物需要单独鉴权并记录调用者、产物编号、节点、开始结束时间、传输字节数、状态和校验结果。Agent 离线、文件缺失或文件过期时返回稳定错误，已有执行记录和产物元数据继续保留。
- 线程栈、直方图和日志片段等文本结果先执行脱敏，再按脱敏后的 UTF-8 字节数判断返回方式。不超过 1 MiB 时，API 和 CLI 返回完整正文，并允许控制端保存及加入诊断包。
- 文本结果超过 1 MiB 时，完整的脱敏内容保存在 Agent 并登记为产物；API 和 CLI 最多返回 256 KiB 的脱敏预览、产物元数据和 `artifact_id`，不把完整正文放入 Agent 命令响应或控制端数据库。
- 只返回预览时，`result_meta.complete` 为 `false`，`reason` 说明正文超过内联上限，`next_command` 给出安全的产物下载命令。`--output raw` 不能绕过正文上限、脱敏或产物权限。
- Heap Dump 始终只返回产物元数据和 `artifact_id`，不生成正文预览；结果通过 `result_meta.complete: false` 和 `next_command` 引导下载。
- Agent 节点上的 Heap Dump、大型日志归档及其他诊断产物统一默认保留 7 天，管理员可以在 7 至 30 天范围内修改保留时间。安装包和源码包不使用该规则。
- 首版不增加节点产物下载限速配置。下载继续使用分块流式中转、断点续传和校验，不把完整文件读入 STX 内存；后续只有出现明确的生产网络问题时再增加限速能力。
- 源码包导入只做首版必需校验：版本与运行包一致、文件名符合对应版本、文件是可读取的 tar.gz，并计算 SHA-256。首版不扫描全部源码内容，也不验证源码能否编译。
- 同版本源码已经存在时，自动下载默认复用已有文件；手工上传或重新下载替换源码时必须显式确认，并以临时文件校验成功后原子替换。替换失败不影响运行包和旧源码。
- 删除某个版本的运行包时，一并删除该版本关联的源码包和安装包列表记录；源码包不能脱离运行包单独形成一条安装包记录。
- 普通业务路由在进入首版 CLI 覆盖清单前需要补齐操作说明；代理、回调、Webhook、SSE 和文件下载等特殊路由必须登记不生成普通命令的原因。CI 需要检查新增路由是否有操作说明或明确的例外登记。
- “首版覆盖全部接口”是指每条实际路由都必须进入操作登记表或例外登记，并接受 CI 检查；不要求每条路由都生成一个可以主动调用的普通 CLI 命令。
- 普通业务 API 生成普通 CLI 命令；诊断和升级等 SSE 事件流使用专用 `watch` 命令；安装脚本、二进制和其他文件资源使用专用 `download` 命令并流式写入文件。
- WebUI 和 Grafana 反向代理登记为代理传输入口，首版不提供允许 CLI 原样转发任意方法、路径和请求体的命令。
- OAuth 回调和 Alertmanager Webhook 等服务端接收入口登记为仅服务端调用，不生成 CLI 命令。登记项仍需说明认证方式、调用方、输入限制、审计规则和测试状态。
- 首版建立服务端操作登记表，并将其作为全部接口的正式清单。每项至少记录稳定 `operation_id`、HTTP 方法、路径、CLI 命令、认证方式、权限、风险等级、确认规则、幂等要求、审计要求、返回类型和测试状态。
- 普通业务路由必须关联一个操作登记项；特殊路由必须关联明确的例外项。CI 检查实际路由、操作登记表、OpenAPI 和 CLI 覆盖结果，任一新增或修改未同步时检查失败。
- CLI 命令树在编译时根据操作登记表生成，并随 `stx` 二进制发布；命令名、离线帮助、Shell 补全和文档不依赖登录或远端服务，不在运行时根据服务端接口动态创建命令。
- 服务端提供登录后可用的 `GET /api/v1/capabilities`。响应返回 `api_version`、`server_version`、`min_cli_version`、`registry_revision` 和当前服务端支持的操作列表。CLI 版本通过 `User-Agent: stx-cli/<version>` 上报，不再使用单独的协议版本 Header。
- 能力列表中的每项操作至少包含 `operation_id`、`revision` 和 `allowed`；无权限时可以返回稳定的 `denial_code`，但不暴露内部权限配置。操作出现在列表中表示服务端支持，未出现表示当前服务端不支持；`revision` 用于检查该操作的请求和响应协议是否兼容。
- `allowed` 只表示查询当时当前用户是否可以使用该操作。CLI 可以用它提前提示无权限，但服务端执行操作时仍要根据用户最新状态和权限重新检查，不能信任旧的能力查询结果。
- CLI 在调用前使用能力信息检查兼容性。操作不存在、修订号不兼容或 CLI 版本低于 `min_cli_version` 时，应在发出业务请求前给出明确的机器可读错误和升级建议。
- 文件上传下载、SSE、代理、二次确认以及组合诊断等特殊交互使用手工适配器，不能仅靠普通 JSON 请求命令生成器处理。
- 服务端新增操作后，需要发布包含对应命令的新 CLI 版本；旧 CLI 仍可调用服务端声明兼容的已有操作。
- STX 首版只维护一份通用 `SKILL.md`，不为不同 AI 工具分别维护内容。该文件使用通用的名称与说明头部，正文不依赖某一种 AI 工具的专有能力。
- `SKILL.md` 说明登录、命名空间、能力发现、风险确认、诊断执行、产物下载、审计查询和敏感信息处理方式，并给出常见排障流程。它不重复列出全部 CLI 命令和接口，而是要求 AI 通过机器可读帮助、操作说明和服务端能力接口取得当前信息。
- 操作登记表、诊断资源登记和 CLI 实际帮助是命令定义来源；`SKILL.md` 只维护稳定的使用方法和安全规则。CI 检查文件引用的核心命令、参数和示例仍然有效。
- `stx skill` 负责查看、安装、更新、查看备份和恢复这一份 `SKILL.md`。首版只管理 `~/.claude/skills/stx` 和 `~/.agents/skills/stx`，`--target` 只接受 `all|claude|agents`，不支持自定义安装目录。`install` 只处理缺失目标，`update` 处理缺失或内容变化的目标；替换前校验摘要、备份旧内容并使用临时目录和原子替换。
- `stx skill show` 把随包的 Skill 原样写到 stdout，不添加说明文字；需要用于其他工具时由使用者手工复制。Skill 安装状态、备份状态和错误结果使用与普通 CLI 一致的机器可读输出。
- 普通 CLI 命令默认输出版本化 JSON，不根据是否处于 TTY 自动改变格式。成功结果写入 stdout，至少包含 `api_version`、`operation_id`、`request_id` 和 `data`。
- `--output json|table|yaml|raw` 是正式输出参数，`--format` 和 `-f` 为兼容别名。AI Agent 和脚本使用 JSON，JSON stdout 不能混入进度文字。
- 普通查询和资源结果支持全局 `--pick field1,field2`。字段裁剪不会绕过脱敏或权限；结果元数据、影响说明和请求编号始终保留。字段不存在时返回安全的完整结果，并在 stderr 给出稳定的 `pick_fallback` 事件。
- 命令登记项必须包含脱敏的使用示例和输出样例。帮助中显示输出样例，CI 校验样例与实际输出结构一致。
- 普通 JSON 结果包含精简的 `result_meta`：`complete` 必填；`reason` 只在结果不完整且需要解释时返回；`next_command` 只在存在安全、明确的后续读取动作时返回。完整结果只返回 `{"complete": true}`。模式、数量和分页信息由具体命令放在自己的 `data` 中。
- `next_command` 只用于安全的查询、分页、等待、详情和下载，不包含令牌、密码、密钥、配置密文或一次性确认编号。
- R2/R3 需要确认时，结果返回结构化 `next_action`，说明确认要求和下一步动作；确认编号不能通过可复制的 `next_command` 暴露。
- stdout 和 stderr 始终分开：stdout 只输出最终业务结果；stderr 使用一行一个 JSON 事件输出进度、警告、影响提示、结果处理状态和错误，不重复完整业务数据。长结果、大文件和事件流使用各自的流式协议，不把全部内容塞进一个 JSON 值。
- 普通 CLI 命令失败时不向 stdout 写业务结果，在 stderr 输出结构化 JSON；错误至少包含稳定的 `code`、可读的 `message`、可选 `details` 和 `retryable`，并返回稳定的非零退出码。
- 表格和 YAML 面向人工阅读，`raw` 用于查看原始 HTTP 响应。文件下载、日志流和事件流另行定义专用输出规则。
- 首版保留现有前端 API 的响应结构，由 CLI 适配器把各模块现有响应转换为统一命令输出，避免因 CLI 上线而要求前端同时修改全部调用。
- 服务端为所有 API 请求生成或接收统一请求编号，并在响应 Header 中返回。CLI 将请求编号放入成功和失败输出，用于查询审计记录、后台任务与 Agent 执行记录。
- CLI 使用普通配置文件保存多个命名空间。每个命名空间可以独立保存 STX 服务地址、令牌、TLS 设置和默认输出等客户端信息，并支持选择当前默认命名空间以及通过命令参数临时指定命名空间。
- 客户端配置支持环境变量覆盖，便于 AI Agent、容器和自动化环境注入服务地址、命名空间与令牌。命令参数、环境变量、当前命名空间配置和内置默认值采用固定优先顺序，且帮助文档必须说明该顺序。
- 不接入操作系统密钥库。包含令牌的普通配置文件必须使用仅当前用户可读写的权限，CLI 输出、日志和错误信息不得显示完整令牌；密码仍只能交互输入或通过标准输入传入，不支持明文命令参数。
- CLI 登录令牌默认有效期为 7 天，服务端允许的最长有效期为 30 天。调用者可以申请更短期限，但不能超过服务端上限；首版不使用刷新令牌，过期后重新登录。
- `stx logout` 在服务端撤销当前命名空间使用的令牌，并从配置文件清除该令牌。用户可以查询和撤销自己在其他命名空间或机器上签发的令牌，管理员可以按权限处理用户令牌。
- 除健康检查、静态资源、指标抓取和 Agent 心跳等明确登记的高频例外外，所有 API 与 CLI 调用都写入审计；登录失败、令牌无效和权限拒绝同样需要记录。
- 普通用户只能查询自己发起的审计记录和命令执行记录，管理员可以查询全部。系统或 Agent 自动产生且无法归属到用户的记录默认仅管理员可见。
- R0 普通查询审计默认保留 30 天；R1、R2、文件下载和敏感信息查询默认保留 180 天；R3、认证、令牌、权限及管理员操作默认保留 365 天。保留期由管理员配置，过期后定时清理，配置变更本身也写入审计。
- 普通查询审计只保存脱敏后的参数摘要、状态、耗时和返回大小，不保存响应正文。SSE、日志流等长连接只记录开始、结束、传输量和结束原因，不记录每段内容。
- 审计记录通过统一请求编号关联确认、后台任务、Agent 命令和文件下载。审计参数必须移除密码、令牌、密钥、配置密文和任务连接凭据。
- SeaTunnel 任务配置可能包含数据库密码、Access Key、Secret Key、Token 等敏感值。任何通过 API、CLI、审计、日志或诊断资源返回任务配置的路径都必须先经过同一套服务端脱敏处理，不能依赖调用方自行隐藏。
- 敏感键识别与替换规则应研究 Apache SeaTunnel 已有的日志脱敏实现，在许可兼容的前提下复用其规则、测试样例或等价语义，并补充 STX 自身的令牌和凭据类型。
- 任务中的秘密采用“只写不读”规则。普通用户和管理员都不能通过 STX API、CLI、网页或 `--output raw` 获取秘密原文；原始值仅保留在服务端用于任务执行，确需找回时由具备数据库权限的人员直接处理。
- 任务查询返回 `******`，同时标明内容已经脱敏及被隐藏的配置路径。`--output raw` 仅跳过 CLI 的输出转换，不能跳过服务端脱敏。
- 带掩码的任务正文再次提交时，同一配置路径上的原掩码表示保留服务端旧值；提交新值表示替换，删除配置项表示删除。掩码与原配置无法可靠匹配时必须拒绝更新，不能把掩码保存成真实配置值。
- HOCON 或 JSON 无法可靠解析、敏感路径无法安全处理时，不返回原始正文，并给出稳定的脱敏失败错误。

## 仓库现状

- 根 Go 程序已经使用 Cobra，发布脚本也已将根程序构建为 `stx`。不过当前根命令仍通过第一个位置参数手工分派 `api`、`scheduler`、`worker`，尚未注册为真正的 Cobra 子命令。
- `scheduler` 和 `worker` 已是遗留兼容壳：对应 `StartScheduler()`、`StartWorker()` 都只返回“legacy mode 已移除”。当前文档也说明默认产品路径不需要启动它们。
- 实际后台能力已经进入 API 进程：API 启动诊断自动策略、节点健康检查、同步预览清理和同步任务定时提交等后台循环。
- 根命令的 `PreRun` 当前会在任何模式下执行数据库迁移。增加远端 CLI 后必须把迁移移到需要它的服务端启动路径，避免 `stx login`、`stx cluster list` 等客户端命令在本机初始化数据库。
- 根命令的 Cobra `Use` 仍是旧值 `linux-do-cdk`，正在进行的“项目改名为 STX”任务需要先处理这个名称。
- 当前登录接口是 `POST /api/v1/auth/login`，成功后通过 Cookie 保存 Gin 会话；受保护接口由 `auth.LoginRequired()` 校验。当前没有 Bearer Token、API Key 或个人访问令牌。
- 当前会话 Cookie 使用服务端配置的密钥签名，并带有有效期、Domain、HttpOnly 和 Secure 配置。CLI 可以复用登录接口和 Cookie，但还没有本地凭据文件约定。
- 当前用户模型只有 `is_active` 和 `is_admin` 两个权限相关字段。除用户管理接口要求管理员外，集群、诊断、任务、插件、升级等接口目前只要求已登录，没有更细的操作权限。
- 前端请求目前只统一设置 JSON Content-Type 和 Cookie，没有设置客户端来源 Header。CLI 专用 Header 需要新增，且该 Header 本身可被伪造，不能单独作为认证依据。
- 现有 HTTP API 已覆盖较多首期候选能力：集群和节点状态、节点日志、监控数据、任务与运行记录、任务日志、Checkpoint 信息、安装包、插件、配置、命令记录、审计记录和升级预检查/执行记录。
- 现有诊断任务已经按固定步骤收集错误上下文、进程事件、告警、配置快照和日志样本，可选收集线程栈与 JVM Dump，并生成机器可读 Manifest、HTML 报告和可下载的诊断包。
- 现有 Agent 只接受 protobuf 中定义的固定命令类型，相关服务将字符串映射为允许的命令；当前 HTTP 路由没有暴露任意 Shell 执行入口。
- 当前审计模型已保存用户、来源 IP 和 User-Agent，但并非每个只读请求都会写审计记录，也没有单独的 CLI 客户端字段。
- 现有同步任务 API 已支持任务预览、提交、运行记录、日志、Checkpoint、恢复和取消；现有升级 API 已支持预检查、计划生成、执行、进度事件与日志。
- 当前没有统一处理 `Idempotency-Key` 的中间件或请求记录。安装包、插件、集群节点等少数服务会按当前状态拒绝重复操作，下载任务也可能返回已存在的任务，但各模块行为并不一致。
- 前端只在部分删除或高影响按钮上自行弹出确认框，服务端不知道用户是否看过影响说明，也没有服务端确认凭据。
- HTTP 方法不能直接代表风险：现有多个 POST 接口实际用于查询、预览或预检查，也有部分 GET 接口会代理访问远端服务。因此风险必须按具体操作定义。
- 诊断、安装、同步和升级已经有各自的异步任务、状态或事件接口，可以复用任务编号返回执行进度，但目前没有跨模块统一的请求关联与重试约定。
- 普通任务取消会立即把内存状态写为 `cancelled`，代码仍留有“向 Agent 发送取消命令”的待办项，实际 Agent 操作不会因此停止。
- 主机安装取消同样没有向 Agent 发送停止命令，而且把状态写为 `failed`、消息写为“安装已取消”；后台安装流程仍可能继续运行并覆盖状态。
- 安装包下载会把任务状态写为 `cancelled`，下载循环在下一次读取前检查该状态并退出，属于协作式停止；但 HTTP 请求没有使用可取消上下文，接口返回时不能证明阻塞中的读取已经结束。
- 插件下载器已经保存 `context.CancelFunc` 并把取消传给下载请求，可以作为本地异步操作真实取消的参考实现。
- 同步任务取消会调用本地停止逻辑或 SeaTunnel 停止接口，但在停止请求返回成功后立即把任务写为 `canceled`，目前没有继续确认远端作业已经进入终态。
- 诊断和升级模型都定义了 `cancelled` 状态，但当前路由没有任务取消接口，也没有把取消请求传到正在执行的步骤或 Agent 命令的完整流程。
- 诊断任务、同步作业和升级任务已经保存数值型 `CreatedBy`；普通 Agent 任务只保存字符串形式的 `CreatedBy`；安装包下载和主机安装状态没有保存发起用户。公共执行记录需要补齐稳定的发起用户编号。
- 当前诊断、同步、安装和升级路由主要只检查用户是否登录，现有取消接口没有统一的执行所有者检查。管理员与其他普通用户能否查看或取消他人执行尚无共同规则。
- 调试工作台任务定义虽然保存 `CreatedBy`，但任务树、列表和详情不按用户过滤，修改、删除、发布、版本回退和调度配置也不检查创建人。`CreatedBy` 当前只是记录字段，不是访问控制依据。
- 调试工作台运行实例保存 `CreatedBy`，但运行列表、详情、日志、Checkpoint、恢复和取消接口没有按发起用户限制；前端会展示选中任务的公共运行历史。
- 调试工作台的全局变量是整个工作台共享资源，创建时保存用户编号，但查询、修改和删除没有所有者限制。秘密值已经脱敏，但谁能使用、修改或删除共享变量仍缺少明确规则。
- 工作台全局变量当前使用全局唯一键；任务运行时会加载全部变量原值，再叠加任务内变量，因此现状无法区分私有变量与共享变量，也无法阻止任务间接使用其他用户的秘密。
- 当前 `/api/v1/audit-logs` 和 `/api/v1/commands` 只要求用户登录，列表和详情没有按当前用户限制。仓库层还存在删除审计记录的方法，但路由目前没有提供审计删除接口，也没有审计导出接口。
- 排除开发环境的 Swagger 页面自身后，当前代码有 239 条 `/api/v1` 路由注册语句，其中包含 4 条 `Any` 代理路由；Swagger 只有 90 个路径、107 个操作。源码中的 `@Router` 注解也正好是 107 条，说明生成器没有遗漏已有注解，缺少的是源代码注解。
- 未进入 Swagger 的注册语句共有 132 条。监控 38 条、同步 33 条、诊断 23 条、升级 9 条、发布包 2 条均没有 `@Router` 注解；集群、插件、Agent 和安装模块还分别缺少 19、5、2、1 条。
- 这 132 条中包含 WebUI/Grafana 代理、Webhook、SSE 和文件下载等不适合按普通 JSON API 描述的接口，但监控、诊断、同步和升级中也有大量普通业务接口缺失，因此这是实际的接口文档欠缺，不只是统计差异。
- Swagger 目前通过 `scripts/swagger.sh` 手工生成；现有 CI 没有运行 `swag init` 或检查生成结果是否与源码一致。
- Apache 官方 2.3.12 发布目录同时提供 `apache-seatunnel-2.3.12-bin.tar.gz` 和 `apache-seatunnel-2.3.12-src.tar.gz`，两类文件各有 SHA-512 校验文件和签名文件。源码包可以按与运行包相同的版本和镜像目录规则获取，但仍需处理部分镜像缺少源码包或校验文件的情况。
- 当前安装包数据结构只有一个运行包文件、路径、大小和 SHA-256；下载请求与下载任务也只有版本和镜像，没有运行包/源码包类型或子任务状态。
- 当前安装包以文件系统目录为准，没有安装包数据库记录。列表只识别 `-bin.tar.gz`，下载任务只保存在进程内存中并按版本作为唯一键，服务重启后任务状态会丢失。
- 当前上传接口一次只接收一个文件，分片上传编号也未区分运行包与源码包；校验只检查版本格式、文件大小和 `.tar.gz` 后缀，没有检查压缩包目录、文件名中的版本或官方校验文件。
- 当前删除只移除运行包，集群安装和升级也只解析、传输运行包路径。新增源码资产后，源码应保留在 STX 控制端，不能进入节点安装或升级流程。
- 仓库中已有 tar.gz 读取和解压代码，但首版源码能力不需要复用这些逻辑；源码包保持压缩文件形态供下载。
- Multica 的实现研究记录见 `research-multica.md`。它的中心 Server 与 CLI 是两个 Go 二进制，但 CLI 二进制同时承担远端客户端和本机 daemon；STX 可以沿用现有单二进制发布方式。
- Multica 的 Public API v1 使用 OpenAPI 3.1、操作登记表、独立 DTO 和统一错误结构，并通过测试检查登记表与 OpenAPI 一致。操作策略包含凭据类型、scope、风险、审计和限流信息，可作为 STX 全接口命令清单的直接参考。
- 当前各模块没有共用的 HTTP 响应类型。多数接口返回 `error_msg` 和 `data`，但也存在使用 `error`、`message` 或模块自定义结构的接口；当前也没有所有请求都携带的统一请求编号。
- 当前只有面向服务端的 `config.yaml`。配置包在初始化时从当前目录或 `CONFIG_PATH` 读取该文件，缺失时会直接退出；远端 CLI 必须使用独立且按需加载的客户端配置，不能依赖或触发服务端配置加载。
- 当前项目没有 CLI profile、令牌文件或系统密钥库集成，也没有相关 Go 依赖；连接多个 STX 地址、本机令牌保存和无交互环境注入方式都需要新增约定。
- 当前 HTTP 审计依靠少数业务处理器手工调用，主要覆盖用户、主机、集群和插件操作；诊断、监控、同步、升级等大量接口没有统一记录。部分 Agent 上报和执行事件会直接写审计表或命令表。
- 当前任意已登录用户都能查询全部审计记录和 Agent 命令记录，没有按调用者限制，也没有仅管理员可查的保护；命令详情还可能包含参数、完整输出和错误内容。
- 当前审计记录缺少请求编号、稳定操作编号、CLI 令牌编号、客户端类型与版本、风险等级、HTTP 状态、耗时、流量、确认编号和幂等键等信息，无法完整关联一次 CLI 请求、后台任务和 Agent 执行。
- 审计仓库已有按时间删除审计记录和命令记录的方法，但没有发现调用这些方法的定时任务、配置项或对外管理入口，现有记录会持续增长。
- 同步工作台已经把 `secret` 类型的全局变量返回为 `******`，更新时提交空值或原掩码会保留旧秘密；这套“秘密只写不读”的行为和测试可以用于任务配置改造。
- 同步任务正文 `content`、发布版本 `content_snapshot`、运行实例 `submit_spec.submitted_content` 和部分预览正文当前仍会通过 API 原样返回。前端会读取任务正文后再次提交完整内容，因此只做显示替换会造成掩码被误存或原秘密被覆盖。
- Apache SeaTunnel 2.3.12 会在打印解析后的配置前递归隐藏 `password`、`username`、`auth`、`token`、`access_key`、`secret_key`，并支持任务通过 `shade.options` 补充键名；当前开发分支还处理分隔符差异、嵌套路径、JDBC URL 和 `sasl.jaas.config`。详细记录见 `research-seatunnel-secret-masking.md`。
- 当前诊断路由整体只使用 `LoginRequired()`，创建和启动诊断任务没有单独的管理员限制。任意已登录用户都可以在任务选项中请求线程栈或 JVM Dump，这与已确认的 R2、R3 规则不一致。
- 现有线程栈采集在 Agent 上先尝试 `jcmd <pid> Thread.print -l`，失败后改用 `jstack -l`；控制端为该命令设置 2 分钟超时。Agent 会把结果写到节点文件，同时把完整文本放进命令响应，控制端再保存一份；当前文件权限为 `0644`，也没有发现线程栈响应大小上限。
- 现有 JVM Dump 在 Agent 上先尝试 `jcmd <pid> GC.heap_dump`，失败后改用 `jmap -dump:live`；控制端超时为 10 分钟。执行前会检查可用磁盘，要求至少达到“配置下限（默认 2 GiB）”和“进程常驻内存估算值的两倍”中的较大值。
- JVM Dump 的 `.hprof` 当前只保存在 Agent 节点；控制端诊断包只记录 JSON 元数据、远端路径和文件大小，并没有传输二进制文件。线程栈则会进入控制端诊断包。
- 当前 Agent 到控制端只有命令结果和日志上报通道，命令结果使用字符串字段。已有的安装包和插件分块传输方向是控制端到 Agent，没有可供控制端按块读取 Agent 诊断文件的通道。要让 CLI 下载节点上的大型诊断文件，需要新增受限的反向分块传输协议，或在文件生成后主动上传到控制端保存。
- 诊断任务通过进程内 goroutine 异步运行，同一个任务按节点依次采集；当前没有发现按 STX、集群、主机、节点或进程设置的并发限制与冷却时间。启动状态检查也不是原子抢占，并发启动同一任务存在重复执行的可能。
- 当前自动诊断策略默认包含线程栈、不包含 JVM Dump，手工诊断任务默认两者都不包含；这与已确认的“自动策略默认不执行 JVM 诊断”不同，需要修改默认值。当前没有直方图命令，Agent protobuf 仅登记了 `THREAD_DUMP` 和 `JVM_DUMP`。
- 当前自动策略路由只要求登录。首版只需要为 Heap Dump 选项增加管理员检查，不新增自动策略授权人、授权版本或长期授权机制。
- 当前没有发现诊断产物的定时删除或保留期配置。Agent 侧诊断目录和控制端诊断包目录使用 `0755`，线程栈及元数据文件使用 `0644`，后续需要改为更严格的文件权限并增加过期清理。
- Oracle JDK 11 将 `Thread.print` 标为中等影响，将 `GC.class_histogram` 和 `GC.heap_dump` 标为高影响；当前 STX 的 `jcmd GC.heap_dump` 未使用 `-all`，按官方说明会请求 Full GC。JDK 8 的命令参数需要向目标 JVM 查询，不能使用 JDK 21 才有的 `GC.class_histogram -parallel`。详细记录和建议默认值见 `research-jvm-diagnostics.md`。
- 当前线程栈和 JVM Dump 的 Agent 结果只有自由文本 `message`，没有供 CLI 或 AI Agent 稳定判断的通用 `impact` 字段。诊断报告中的 `ImpactSummary` 只用于组合诊断包的 HTML 健康摘要，不能直接替代单项执行结果的影响说明。
- 当前 `DefaultDiagnosticTaskSteps()` 固定返回 10 个步骤。错误上下文、进程事件、告警、配置等步骤始终执行，只有线程栈和 JVM Dump 由布尔选项控制，现有模型还不能任意选择资源组合。
- 现有 10 个步骤中，Manifest、HTML 报告和完成标记是内部流程，不对应可供 AI 获取的独立证据。公开的诊断资源不能直接等同于全部现有步骤编码。
- 部分现有采集函数依赖同一任务中更早步骤写入的内存状态。例如日志采集会使用错误上下文步骤得到的错误事件，多个步骤会使用巡检详情确定时间窗口。改为单项执行时，每个资源执行器需要显式声明依赖，或能根据本次请求自行加载必要上下文，不能依靠隐藏的固定执行顺序。
- 当前指标快照不是独立步骤，而是在“告警快照”步骤中顺带查询 Prometheus 并另存 `metrics-snapshot.json`。独立资源登记时应将告警和指标分开。
- 当前“配置快照”同时读取集群部署信息、多个 SeaTunnel 配置文件、配置变更历史，以及 `config`、`lib`、`connectors`、`plugins` 四个目录的文件清单。为了支持按需采集，部署信息、配置文件和 JAR/插件目录清单不应继续绑定为一个资源。
- 当前同步模块已经提供任务列表、版本、提交实例、运行详情、日志和 Checkpoint 查询，但这些数据尚未作为可加入诊断包的资源登记。
- 当前没有采集系统环境变量或 JVM 类直方图的诊断资源；源码包关联与下载也仍属于本次方案中的新增能力。
- 当前没有 JFR、async-profiler 或火焰图实现。JDK 8/11、native 工具、权限和平台差异的调查记录保留在 `research-flame-graph.md`，但火焰图及相关工具分发已经决定不纳入首版。

## 暂不纳入

- 向 AI Agent 提供不受限制的 SSH、Shell 或任意文件读写能力。
- 审计记录文件导出以及 `stx audit export` 命令。
- 绕过 STX 已有权限模型直接访问 SeaTunnel 节点。
- 允许客户端仅凭来源 Header 获得更高权限。
- 在 STX 服务端解压、建立索引、搜索或读取源码文件内容。
- 单独部署 STX Scheduler 或 Worker 服务。
- 将 `stx-agent` 合并进 `stx`，或让 Agent 携带控制端 CLI 的全部代码和依赖。
- 火焰图、JFR 录制资源以及 async-profiler 的安装和管理。相关调查资料保留，后续有明确需求时另行设计。
- 不修改集群的模拟升级模式；首版只提供现有升级预检查和受 R3 保护的真实升级流程。

## 验收条件（初稿）

- [ ] 用户可以配置 STX API 地址并完成登录、凭据复用和退出。
- [ ] `stx` 可以启动唯一的 STX API 服务，也可以在不初始化本地数据库的情况下作为远端客户端运行；发布物中不再要求启动独立 Scheduler 或 Worker。
- [ ] `stx server` 是正式服务端入口；`stx` 无参数只显示帮助；`stx api` 在一个版本的兼容期内仍能启动相同服务，但不会出现在普通帮助中。
- [ ] `stx-agent` 继续独立构建和发布，新增 CLI 不增加 Agent 的控制端依赖。
- [ ] CLI 请求携带 `Authorization: Bearer <token>`、`X-STX-Client: cli` 和 `User-Agent: stx-cli/<version>`；服务端可以区分 CLI 与前端请求，并在审计中分别记录认证方式、客户端类型和客户端版本。
- [ ] `X-STX-Client` 和 `User-Agent` 不参与认证与权限判断；伪造这两个 Header 不会取得额外权限。
- [ ] CLI 的命令、参数、退出码、标准输出和标准错误有稳定约定，AI Agent 无需解析网页或交互式提示。
- [ ] 现有 STX 接口覆盖清单中的每个接口都有明确处理结果：对应 CLI 命令、专用传输方式，或注明不直接调用的原因和替代入口。
- [ ] 约 239 条现有 `/api/v1` 路由全部进入操作登记表或例外登记；CI 能发现实际路由、OpenAPI、CLI 与登记内容不一致。
- [ ] 普通业务 API、SSE 和文件资源分别生成普通命令、`watch` 命令和 `download` 命令；WebUI/Grafana 代理、OAuth 回调和 Alertmanager Webhook 不会生成可原样转发的 CLI 命令。
- [ ] 未生成 CLI 命令的特殊路由仍有稳定登记项、原因、认证或调用方说明、审计规则和自动化测试，不会从覆盖统计中消失。
- [ ] CLI 命令、帮助、补全和文档可以由操作登记表重复生成，生成后仓库无未提交差异；普通命令无需连接服务端即可发现。
- [ ] 仓库和发布物只维护一份通用 `SKILL.md`；文件不会复制维护全部操作列表，而是引导 AI 查询 CLI 的机器可读帮助和能力接口。
- [ ] CI 能验证 `SKILL.md` 中使用的核心命令、参数和示例，CLI 变更造成引用失效时检查失败。
- [ ] `stx skill show|status|install|update|backup|restore` 可以管理随包的唯一 Skill 源文件；首版只安装到 `~/.claude/skills/stx` 和 `~/.agents/skills/stx`，不接受其他目标或任意路径；更新已有目标前会备份并原子替换，失败时可用备份恢复。
- [ ] 所有普通命令支持 `--output`，并接受 `--format`、`-f` 别名；JSON stdout 可以直接被 JSON 解析器读取。
- [ ] 支持 `--pick` 的命令只裁剪安全的顶层字段，始终保留结果元数据、影响说明和请求编号；字段不存在时返回安全完整结果并写出 `pick_fallback` 事件。
- [ ] 命令帮助包含脱敏的使用示例和输出样例；通用 `result_meta` 只包含必填的 `complete` 以及按需返回的 `reason`、`next_command`，数量和分页信息留在具体命令的 `data` 中。
- [ ] 分页或结果不完整且存在安全后续动作时，结果元数据包含可执行且不含敏感信息的 `next_command`；完整结果只需返回 `{"complete": true}`。
- [ ] 结果中的 `next_command` 不包含令牌、密码、密钥、配置密文或一次性确认编号；R2/R3 使用单独的 `next_action` 表达确认步骤。
- [ ] 登录后的用户可以调用 `GET /api/v1/capabilities`，响应包含 `api_version`、`server_version`、`min_cli_version`、`registry_revision`，以及带 `operation_id`、`revision`、`allowed` 和可选 `denial_code` 的操作列表。
- [ ] CLI 能区分服务端不支持、操作修订号不兼容和当前用户无权限；前两种情况不会发送可能产生影响的业务请求。
- [ ] 能力查询中的 `allowed` 不替代执行时权限检查；用户被禁用或权限变化后，即使 CLI 使用旧的查询结果，服务端仍按最新权限拒绝请求。
- [ ] 同一普通命令在交互终端和非交互环境中的默认 JSON 结构一致；最终业务结果只写 stdout，进度、警告、影响提示、处理事件和错误只写 stderr；失败命令返回文档规定的非零退出码。
- [ ] 每次 API 调用都有响应请求编号，CLI 输出中的请求编号可以查到对应审计记录；现有前端调用在首版仍能按原响应结构工作。
- [ ] CLI 可以在普通配置文件中维护并切换多个命名空间，环境变量能够覆盖当前配置，配置优先顺序经过自动化测试并写入帮助。
- [ ] 新建令牌默认 7 天过期且不能申请超过 30 天；退出会撤销服务端令牌并清除本机记录，配置文件、日志和命令输出不会泄露完整令牌。
- [ ] CLI 令牌没有独立权限范围或权限快照；相同用户使用网页会话和 CLI 令牌访问同一操作时，服务端依据同一份用户当前权限作出决定。
- [ ] 用户被禁用、删除或权限改变后，尚未过期的 CLI 令牌立即受到影响；令牌列表和签发接口不提供另一套权限配置。
- [ ] 除明确登记的高频例外外，每次 API/CLI 调用均能查到审计记录；普通用户不能查看其他用户的记录或 Agent 命令输出，管理员可以按条件查询全部。
- [ ] 不同风险类别的审计记录按 30、180、365 天默认策略自动清理，管理员可调整保留期，清理和配置变更都有测试与记录。
- [ ] 包含密码、密钥或令牌的 SeaTunnel 任务经过 API、CLI、审计、日志和诊断资源返回时均显示脱敏值，原始秘密不会因 `--output raw` 或管理员身份被意外返回。
- [ ] 带掩码的任务经网页、API 或 CLI 读取后不修改秘密再次保存，原秘密仍可用于运行；替换和删除秘密有明确语义，路径歧义或脱敏失败时不会写入错误内容或返回原文。
- [ ] 每个查询命令都有机器可读输出、权限检查、超时、大小限制和敏感信息处理规则。
- [ ] 每个有状态操作都有明确权限、风险等级、二次确认规则、幂等规则、执行状态、失败结果和可追踪记录。
- [ ] R1 命令在非 TTY 环境中未提供 `--confirm` 时不会修改远端状态；TTY 用户确认后可以由 CLI 继续执行。
- [ ] R2、R3 命令未提供有效 `--confirmation-id` 时只返回影响说明和结构化 `next_action`，不会开始远端操作；TTY 用户确认后可以由 CLI 自动提交第二次请求。
- [ ] 非 TTY 环境不会出现交互式问题；R2、R3 不能通过 `--yes` 或布尔型 `--confirm` 跳过服务端签发的一次性确认编号。
- [ ] CLI 为 R1、R2、R3 请求自动生成幂等键，也允许通过 `--idempotency-key` 指定；自动重试和 R2、R3 的两次确认请求复用同一个键。
- [ ] 相同用户、`operation_id`、幂等键和请求内容不会重复执行；执行中可返回原执行编号，执行结束后可返回原结果或结果引用。相同键对应不同请求时返回 HTTP 409 和 `idempotency_conflict`。
- [ ] 运行中的幂等记录不会被清理；结束记录至少保留 24 小时，过期清理不删除对应审计记录。
- [ ] 可修改资源返回资源 `revision` 和可用的 `ETag`；CLI 对需要版本保护的更新、删除和执行操作支持 `--revision`，并使用 `If-Match` 提交条件请求。
- [ ] 资源在读取后发生变化时，服务端返回 HTTP 409 和 `revision_conflict`，不产生目标操作的远端影响；调用者重新查询后才能再次修改或申请 R2、R3 确认。
- [ ] 能力查询中的操作协议修订号与业务资源版本有明确区分；没有资源版本保护的旧接口必须在操作登记表中说明限制及 CLI 是否可用。
- [ ] 所有向 CLI 暴露的异步操作都返回稳定 `execution_id`，可以通过 `stx execution get|wait|cancel` 查询状态、等待完成和申请取消，同时仍能查看模块自己的步骤、日志与结果。
- [ ] 执行记录以 `owner_user_id` 归属用户；更换令牌、命名空间、机器或客户端不会改变所有者，同一用户的其他有效登录方式仍能管理该执行。
- [ ] 普通用户不能查看或取消其他用户的执行；管理员按权限管理全部执行。用户被禁用或失去操作权限后，旧令牌不能继续管理执行。
- [ ] 公共执行状态能够稳定表示等待、运行、请求取消、正在取消、已取消、成功、失败和超时；模块内部状态都有明确映射并经过测试。
- [ ] 执行记录返回 `cancellable` 和不能取消的稳定原因。不可安全停止或已经来不及停止时，不会把执行状态写成 `cancelled`。
- [ ] 取消请求会传到实际执行者；只有实际执行已经停止并收到确认后才进入 `cancelled`。普通任务、安装、下载、同步、诊断和升级分别有覆盖成功取消、取消失败及完成与取消竞争的测试。
- [ ] 取消操作幂等；重复请求不会发送多次有副作用的停止命令。已经进入终态的执行不会被迟到的后台更新改成另一个终态。
- [ ] 需要清理或恢复的操作会记录对应状态和结果；清理或恢复失败时返回稳定错误并保留真实执行状态，不把未完成流程报告为取消成功。
- [ ] `execution get|wait` 按 R0 处理；普通下载和纯证据采集取消按 R1 处理；停止 SeaTunnel 作业或影响服务的 Agent 操作按 R2 处理；中断安装、升级和回滚按 R3 处理。
- [ ] R1 取消使用 `--confirm`，R2、R3 取消使用服务端确认编号，R3 还要求管理员权限；`cancellable: false` 的执行不会签发无效确认编号。
- [ ] 调试工作台新建任务默认私有；私有任务只有所有者和管理员可以查看、编辑、删除、发布和运行，所有者可以显式改为共享。
- [ ] 共享任务允许具备权限的其他用户查看和运行，但只有所有者和管理员可以编辑、删除、发布、修改共享范围和修改调度配置；任务版本执行相同规则。
- [ ] 预览、提交和恢复产生的执行归实际发起用户所有；共享任务不会让普通用户看到其他用户的运行历史，管理员可以按权限查看全部执行。
- [ ] 新数据库结构直接保存任务所有者和共享范围，不包含旧任务迁移、默认所有者推断或兼容旧权限行为的分支。
- [ ] 全局变量默认私有，所有者可以显式设为共享；私有变量只能被所有者的任务和管理员任务引用，共享变量允许有工作台使用权限的其他用户任务引用。
- [ ] 全局变量的查看、修改、删除和共享范围变更按所有者或管理员权限检查；任务运行时不能加载当前任务无权引用的变量。
- [ ] 秘密变量在列表、详情、CLI、API、日志、审计和任务结果中始终只显示掩码，管理员也不能通过产品接口取回明文。
- [ ] 变量引用、实际使用者和任务写入审计；审计记录不保存变量原值、配置密文或可还原秘密的内容。
- [ ] 普通用户只能查看自己发起或归属于自己的审计记录，管理员按权限查看全部记录；系统自动执行默认只对管理员可见，关联用户任务或执行时允许对应所有者查看相关记录。
- [ ] 审计事件不提供修改或按条删除接口；命令状态变化不会改写历史审计事件，并为关键状态变化新增不可修改的事件记录。
- [ ] 审计过期清理由服务端保留策略执行，清理动作本身可查询；首版没有审计导出 API、文件下载入口或 `stx audit export` 命令。
- [ ] `help` 可以显示命令的远端行为、目标资源、风险等级、是否需要确认、是否调用 Agent 以及可能的性能影响。
- [ ] 诊断中心可以列出全部已登记资源及其稳定编码、参数、风险、影响、超时、执行位置、结果类型和是否允许加入诊断包。
- [ ] 每项公开诊断资源都可以通过网页、API 和 CLI 单独执行并留下执行记录；单项采集不会强制运行其他无关资源或生成完整诊断包。
- [ ] CLI 默认等待单项资源执行结束并返回结果；使用 `--detach` 时立即返回执行编号，后续可以根据编号查询状态、等待完成及下载产物。
- [ ] 一键诊断包可以勾选多个已登记资源，并调用与单项执行相同的资源执行器；相同参数下，两种入口的资源结果格式一致。
- [ ] Manifest、HTML 报告和完成标记只作为组合任务的内部流程，不出现在可采集资源列表中。
- [ ] 单项资源所需的时间窗口、错误来源和节点信息通过明确参数或已登记依赖取得，不依赖某个未执行的前置步骤留下的进程内状态。
- [ ] Agent 仅执行注册过的命令和参数，未知命令、越界路径、过大输出和超时操作会被拒绝或终止。
- [ ] 除 `heap-dump` 外，诊断命令不会仅因诊断专用的频率或冷却规则而被拒绝；普通容量、超时、权限、确认、幂等和审计规则仍然生效。
- [ ] 同一 JVM 10 分钟内只能实际开始一次 `heap-dump`，其他节点或 JVM 不受影响；重复请求不会触发 Agent 命令，错误中包含稳定编码、剩余等待秒数和下次允许时间，并能查到审计记录。
- [ ] `heap-dump` 使用集群、节点、PID 和 JVM 启动时间识别同一目标；JVM 重启或 PID 被系统重复分配时不会错误沿用旧进程的等待时间。
- [ ] 同一个 JVM 同一时间最多运行一个线程快照、类直方图或 Heap Dump；不同 JVM 可以并行执行。
- [ ] 目标 JVM 忙时新请求不排队且不调用 Agent，返回 `target_busy`、占用中的 `execution_id`、资源类型和可执行的查询或等待命令；被拒绝的请求不会启动 Heap Dump 十分钟计时。
- [ ] JVM 诊断命令尚未发送给 Agent 时都可取消；取消成功后不会继续发送命令，并释放目标 JVM 的互斥占用。
- [ ] 线程快照和类直方图开始后，取消请求会传给 Agent；只有工具进程停止并清理未完成临时产物得到确认后，执行才进入 `cancelled`。
- [ ] Heap Dump 在 Agent 上开始后返回 `cancellable: false` 和 `heap_dump_already_started`；停止 `jcmd` 或 `jmap` 客户端不会被当作 Heap Dump 已停止的证据。
- [ ] Agent 离线、取消超时或无法确认工具进程停止时，执行不会被错误写成 `cancelled`；命令已完成时返回 `too_late_to_cancel` 和真实终态。
- [ ] 自动诊断策略默认不执行线程快照、类直方图和 Heap Dump；只有策略中明确勾选的 JVM 诊断资源才可能自动执行。
- [ ] 自动策略中的 Heap Dump 只能由管理员勾选、保存和启用；线程快照和类直方图不增加额外授权流程。
- [ ] 自动执行的 JVM 诊断与人工执行共用目标互斥、Heap Dump 十分钟限制、影响说明、产物保存、审计和取消规则。
- [ ] 线程栈、直方图和 JVM Dump 的确认预览、成功结果及失败结果都包含与资源登记一致的影响说明；JSON 中可通过稳定字段判断它是否可能影响集群，人工输出能直接看到对应文案。
- [ ] `heap-dump` 的结果明确说明 Full GC、目标 JVM 暂停、磁盘空间和磁盘 I/O 风险，以及这些现象可能对节点任务和集群运行造成的影响。
- [ ] 脱敏后的文本诊断结果不超过 1 MiB 时返回完整正文；超过 1 MiB 时，完整脱敏内容只保存在 Agent，API 和 CLI 最多返回 256 KiB 的脱敏预览及产物元数据。
- [ ] 文本结果只返回预览时，`result_meta.complete` 为 `false`，并返回原因和安全的下载命令；`--output raw` 不能绕过正文上限、脱敏和产物权限。
- [ ] Heap Dump 只返回产物元数据和下载命令，不返回正文预览，也不会进入控制端数据库或普通命令输出。
- [ ] CLI 可以运行现有升级预检查，但结果不会被描述为真实升级成功；真实升级必须明确指定集群和目标版本，并经过管理员权限检查、R3 二次确认、冒烟测试及失败回滚。
- [ ] 首版不存在跳过真实升级步骤却返回“升级测试成功”的模拟命令或接口。
- [ ] CLI 可以调用现有配置校验、连接测试、受限数据预览和真实任务提交；相同输入与网页调用使用同一套执行逻辑和任务记录。
- [ ] 数据预览保留行数与超时限制，并在结果中说明实际运行目标和可能影响；真实任务提交明确指定目标集群，经过 R2 二次确认和幂等检查。
- [ ] AI 发起的任务不会产生另一种任务类型，可以通过审计中的调用来源、用户、令牌编号和请求编号查询。
- [ ] 一次 CLI 调用从 HTTP 请求到 Agent 执行及结果返回具有统一关联标识，可以在审计查询中还原调用者、目标、操作、确认信息、结果和耗时。
- [ ] 审计数据不保存密码、Session Cookie、认证令牌、配置密文或未限制大小的原始 dump 内容。
- [ ] CLI 不提供任意 Shell 或任意文件访问入口，错误输入不能越过服务端设定的资源范围。
- [ ] 在 AI 无法直连 SeaTunnel 节点的测试环境中，可以仅通过 STX CLI 收集一次典型故障所需的证据。
- [ ] CLI 用法可以被 AI Agent 独立发现，并有可验证的示例和自动化测试。
- [ ] 安装包下载默认同时获取同版本 SeaTunnel 源码，并能分别显示运行包与源码包的下载状态、大小、校验值和失败原因。
- [ ] 源码自动下载失败时运行包仍可用于安装和升级；用户可以查看失败原因并只重试源码下载。
- [ ] 手工导入必须接受运行包，允许同时提供同版本源码包；运行包成功后立即出现在本地安装包列表，源码处理结果不会撤销运行包。
- [ ] 本地安装包列表有独立的源码状态列；未导入或导入失败时，可以按当前版本联网补充源码或单独手工上传源码。
- [ ] 源码版本不一致或源码压缩包不合法时给出明确错误，并保持已有运行包可用。
- [ ] 删除运行包时会按已确定规则处理关联源码，源码包不会被分发或安装到 SeaTunnel 节点。
- [ ] AI Agent 可以通过 API/CLI 查看源码包元数据并下载完整源码包；STX 首版不解压、不建立索引，也不提供源码内容读取接口。
- [ ] Heap Dump 和大型日志归档默认只保存在生成文件的 Agent 节点；STX 能根据受控产物编号分块中转到 CLI，控制端不会留下长期文件副本。
- [ ] 节点产物下载支持中断后按偏移继续，并在完成前校验长度和 SHA-256；校验失败时不会把临时文件当作完成文件。
- [ ] 客户端不能通过下载接口读取未登记路径；Agent 离线、产物缺失或过期时返回稳定错误，下载尝试和实际传输量均能在审计中查询。
- [ ] Agent 节点诊断产物默认在生成 7 天后自动删除；管理员只能把统一保留时间配置为 7 至 30 天。
- [ ] 首版节点产物下载没有应用层限速配置，但采用分块流式中转，不会把完整大型文件读入 STX 内存。
- [ ] 源码包校验版本、文件名、tar.gz 可读性和 SHA-256；替换使用临时文件校验与原子替换，失败时保留已有运行包和旧源码。
- [ ] 删除运行包会同时删除关联源码和对应列表记录；源码不会脱离运行包单独出现在安装包列表。

## 开放问题

CLI 首版的需求范围已经确认。后续进入技术方案时，只处理实现所需的接口契约、包结构、命令映射和测试计划，不再扩展自动策略等旁支功能。
