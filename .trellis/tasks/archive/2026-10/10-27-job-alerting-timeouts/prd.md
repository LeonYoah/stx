# 作业层级告警与引擎超时治理

## Goal

作业出问题时要有人知道，不能等有人碰巧打开页面才发现。SeaTunnel 集群很忙、接口很慢时，STX 也不能出现以下情况：
- 判错状态；
- 丢掉作业；
- 重复提交；
- 一个集群慢，拖慢所有集群。

用户要求（2026-10-27）：
- 梳理代码和场景，做**作业层级的整套告警设计**，同时考虑各类超时。
- 提交超时**默认 5 分钟，可以自定义**。

## 已确认事实（代码）

### 告警模块（`internal/apps/monitoring`）
- **链路**：
  - 进程事件 `monitor.ProcessEvent`（`process_events` 表）由 `monitorService.RecordEvent` 写入。
  - 写入后回调 `monitoring.DispatchAlertPolicyEvent`（`router.go:378`）。
  - 回调按"集群 + 规则键"查出启用的策略（`ListEnabledAlertPoliciesByClusterAndLegacyRuleKey`）。
  - 再给策略绑定的渠道发通知，并记录 `monitoring_notification_deliveries`。
- **策略**（`AlertPolicy`，`entity.go:46`）：
  - 字段：模板键、集群（**精确到单个集群**，带规则键的模板不允许选"全部集群"）、级别、启用、冷却分钟（到点重发提醒）、是否发恢复通知、条件（`metric_key`、比较符、阈值、窗口分钟）、通知渠道、接收人。
  - 策略中心前端：`MonitoringPolicyCenter.tsx`。
- **渠道**：webhook、邮件、企业微信、钉钉、飞书。
- **"持续状态"类告警**只有"节点离线"：
  - 后台评估器 `EvaluateNodeHealthAlerts` 发 `node_offline` 事件，恢复时发 `node_recovered`。
  - 告警持续期间按冷却时间重发提醒，恢复后发恢复通知。
  - 作业类的"持续状态"告警可以照这个模式做。
- **现有规则**：
  - 进程类：崩溃、重启失败、达到重启上限、手动重启或停止、节点离线。
  - Prometheus 指标模板：CPU、堆内存、FD、`failed_jobs_high`（引擎 `job_count{state=FAILED}`，只有数量，不知道是哪个作业）、线程池、死锁、脑裂。
- **sync 模块目前不产生任何告警。**

### 作业侧能拿到的信号（`internal/apps/sync`）
- 状态：`pending / running / cancel_requested / cancelling / doing_savepoint / failing / success / failed / canceled / savepoint_done`。
- 对账每 10 秒拉一次：running 列表、6 个 finished 列表、每个作业的 job-info。拿到的有状态、错误信息、读写条数（`SourceReceivedCount` / `SinkWriteCount`，每 30 秒记一笔 `metrics_log`）、DAG。
- 引擎丢失作业（集群重启、历史过期）：对账判 FAILED，错误写"引擎已无此作业"。
- 同步状态：`sync_state` 为 `ok`、`degraded`、`stale`；连续失败计数 `sync_fail_count`。
- 3.x 并开启事件通道时，额外能拿到：
  - CDC 延迟（内存聚合 `cdc_delay`）；
  - DDL 事件；
  - 通道健康状态（降级判断）。
- 3.x 并开启可观测性时，有背压和忙碌度。但只在有人查看时才去拉（`/realtime`），后台不采集。
- Checkpoint 概览接口有失败次数和最近成功时间，同样只在有人查看时才拉。
- 触发来源：手动、CLI、内置定时、Dolphin（`trigger_source`）。内置定时提交失败**只写日志**。

### 超时现状
| 调用 | 超时 | 超时后 |
|---|---|---|
| 提交 `submit-job` | 15 秒 | 当作失败，不留记录；会改走 v1 再提交一次（见子任务 `10-26-submit-timeout-recovery`） |
| 停止 `stop-job` | 15 秒 | 状态恢复成运行中，提示"停止请求失败"；引擎可能其实已经在停 |
| running/finished 列表、job-info | 每次 15 秒 | 不改状态，只把 `sync_state` 标成 degraded/stale；**各集群串行**，一个慢集群拖慢所有集群；没有退避 |
| 停止中（cancelling） | **没有上限** | 一直显示"停止中" |
| checkpoint、日志 | 15 秒 | 页面报错 |
| `/realtime` | 3 秒，带缓存 | 返回 `available=false` |
| 事件触发的刷新 | 每次 20 秒，最多 4 个并发 | 下一轮再试 |

### 配置现状
- 全局配置只有 `config.yaml` 的 `sync:` 段，没有界面上可改的系统设置。
- 任务级设置写在 `task.Definition`，前端在 `SettingsSidebarPanel.tsx`，可观测性开关就是这样做的。

## Decisions

- 2026-10-27 分期（用户确认）：
  - **第一期**：A1、A2、B1、C1、D1、D2。只用现有信号，不增加引擎调用。
  - **第二期**：B4。需要调阈值、处理误报。
  - **以后**：B5、B6。会增加引擎调用，与"压力大时少调接口"冲突。
  - **不做**：B2（批作业运行超时）、B3（实时作业没有数据）。用户 2026-10-27 明确去掉。
- 2026-10-27 告警路由（用户确认，后经修正）：
  - **集群级告警（D1、D2）**：按集群配置策略，复用现有的告警策略、渠道、静默和确认，**默认开启**。跟"节点离线"一样，作为每个集群的默认规则，告警中心默认就能看到。要发通知，得有策略和渠道。
  - **作业级告警（A1、A2、B1、C1）**：用户原话是"告警是作业级别的，告不告警看用户配不配置"。用户在任务上配置了告警才会告警，没配就不告警，**不做额外的开关**。之前提议的"任务级开关"已撤回。
  - 保留"同时通知任务创建人"这个选项。
  - 只排除 `run_type=preview`（数据预览）。核实结果：工作台点"运行"或"恢复"，**总是**带编辑器内容作为 `draft` 提交（`DataSyncStudio.tsx` 约 3650 行），实时任务的正式运行一般就是这样发起的，所以不能按草稿排除。
- 2026-10-27 超时可配置（用户确认）：**全局默认加任务覆盖**。
  - 提交超时：全局 `config.yaml` 默认 5 分钟。超过这个时间引擎里还没有这个作业，判定提交失败，触发 A2。
  - 停止超时：全局默认 5 分钟。超时后触发 C1，作业保持"停止中"，不改成失败。
  - 任务设置里可以分别覆盖，留空表示用全局默认。任务里的值存在 `task.Definition`，跟着任务版本走，改了要重新发布才生效，和"可观测性"设置一致。
- 2026-10-27 告警合并（用户确认）：**按"任务 + 问题类型"合并成一次告警阶段**。
  - 阶段内首次出现时发告警，之后不再重复发送，只累计"已连续 N 次"。
  - 问题一直没解决时，按策略的冷却时间重发提醒。
  - 恢复时发恢复通知。各类型的恢复条件：
    - A1、B1：任务下一次提交成功并跑起来。批作业要跑成功（success）；实时作业进入运行中（running）。
    - A2：作业被确认，或者下一次提交成功。
    - C1：作业最终停下。
- 2026-10-27 作业告警配置入口（用户确认）：
  - **在任务设置侧栏配置**，内容包括：勾选告警情况（提交失败、提交超时、作业失败、停不下来）、通知渠道、接收人、是否同时通知创建人。
  - 没配置时，侧栏只显示一行"未配置告警"。
  - 底层存成**以任务为范围的告警策略**，复用告警中心、静默、确认、投递记录和渠道。策略中心可以按任务筛选，统一查看和修改。
  - 告警配置**不跟随任务版本**，改了立即生效，不需要重新发布。

## 场景清单

| # | 场景 | 现在 | 信号来源 | 额外引擎调用 |
|---|---|---|---|---|
| A1 | 提交失败（引擎明确拒绝） | 只报错给点运行的人；定时或 Dolphin 触发时没人看见 | 提交返回值 | 无 |
| A2 | 提交超时未确认（默认 5 分钟） | 不留记录 | 子任务 1 | 无 |
| B1 | 作业失败（包括引擎丢失作业） | 只在列表里显示 | 对账 | 无 |
| B2 | 批作业运行超时（超过 N 分钟没结束） | 无 | 对账，加上开始时间 | 无 |
| B3 | 实时作业没有数据（N 分钟读写条数都不增长） | 无 | 对账的 metrics | 无 |
| B4 | CDC 延迟过高（大于 N 秒，持续 M 分钟） | 只显示徽标 | 事件通道 | 无（仅 3.x 且开启通道） |
| B5 | Checkpoint 长时间不成功 | 无 | checkpoint 概览 | **有**：每个实时作业定期多调一次 |
| B6 | 背压或瓶颈 | 只在有人查看时提示 | `/metrics/realtime` | **有**：后台采集 |
| C1 | 停止超时（停止后 N 分钟仍没停下） | 一直显示停止中 | 对账 | 无 |
| D1 | 作业状态获取失败（集群级，持续 N 分钟） | 只有页面上的"同步延迟" | `sync_state` | 无 |
| D2 | 事件通道降级（集群级） | 只在集群卡片上显示 | 通道健康 | 无 |

## 子任务（执行顺序 1 → 2 → 3）

| 顺序 | 子任务 | 交付 | 依赖 |
|---|---|---|---|
| 1 | `10-26-submit-timeout-recovery` | 提交、停止结果未知时登记作业，由对账确认；确认前拦截重复提交；提交超时和停止超时用"全局默认 5 分钟 + 任务覆盖" | 无 |
| 2 | `10-27-job-alerts` | 作业级告警（A1、A2、B1、C1）在任务设置里配置；集群级告警（D1、D2）默认开启；告警阶段、通知、告警中心、深链、CLI | 依赖 1 提供的过期和停止超时接入点 |
| 3 | `10-27-engine-query-resilience` | 各集群并行对账、本轮遇到超时即停止、按集群退避、请求超时可配置 | 建议在 1 之后做（复用错误分类）；和 2 的顺序可以调换，见其 design §6 |

第二期（B4 CDC 延迟告警）等第一期上线后再单独建任务。
