# 作业告警第一期：任务级告警配置与集群级默认规则

> 父任务：`10-27-job-alerting-timeouts`。依赖子任务 `10-26-submit-timeout-recovery`：要用它提供的提交过期、停止超时这两个状态和接入点。必须在它合并后开工，或者基于它的分支开工。

## Goal

作业出了问题，配了告警的任务要能把通知发出去；集群层面观测不到作业时，默认就能在告警中心看到。现在 sync 模块完全不产生告警，只能等人打开页面才发现问题。

## Decisions（2026-10-27，用户确认，详见父任务 prd）

- 第一期场景：
  - 作业级：A1 提交失败、A2 提交超时、B1 作业失败、C1 停止超时。
  - 集群级：D1 作业状态获取不到、D2 事件通道降级。
- 作业级告警由**用户在任务上配置**：配了才发，不配不发，不额外做开关。配置入口在**任务设置侧栏**，底层存成**以任务为范围的告警策略**，改了立即生效，不跟随任务版本。可选"同时通知任务创建人"。
- 集群级告警**默认开启**：做法和"节点离线"一样，作为每个集群的默认规则，在告警中心能看到。要发通知，得配好策略和渠道。
- 只排除 `run_type=preview`（数据预览）。工作台里的运行不排除。
- 合并：同一个"任务 + 问题类型"（集群级则是"集群 + 问题类型"）算作一次告警阶段：
  - 阶段里第一次出问题时发一次通知，之后只累计次数。
  - 问题一直没解决，按冷却时间重新提醒。
  - 问题恢复时发恢复通知。

## Requirements

### R1 规则目录

| 规则键 | 场景 | 范围 | 默认级别 | 触发 | 恢复 |
|---|---|---|---|---|---|
| `sync_submit_failed` | A1 | 任务 | critical | 提交到引擎被明确拒绝，或者找不到可用的引擎端点 | 这个任务下一次健康运行* |
| `sync_submit_timeout` | A2 | 任务 | critical | 提交结果一直是未知，直到过了截止时间，作业被判 FAILED（expired） | 同上 |
| `sync_job_failed` | B1 | 任务 | critical | 作业状态转为 failed，包括"引擎已无此作业"的情况；A2 过期判失败的作业**不重复报** B1 | 同上 |
| `sync_stop_timeout` | C1 | 任务 | warning | 过了 `cancel_deadline` 作业仍未停下 | 这个作业到达终态 |
| `sync_status_unavailable` | D1 | 集群 | warning | 集群的 running 列表连续拉取失败（或者找不到端点）达到规则窗口，默认 300 秒 | 第一次拉取成功 |
| `sync_event_channel_degraded` | D2 | 集群 | warning | 事件通道状态从健康变为降级 | 重新变为健康，或者通道被关闭 |

\* **健康运行**：批作业运行成功（success），实时作业进入运行中（running）。

- A1 只统计"和引擎打交道失败"的情况。下面这些属于用户操作错误，**不触发告警**：参数校验失败、没有权限、未发布、409 拦截。
- 第一期每条规则的级别固定为表里的默认值，不支持配置。

### R2 任务告警配置（任务设置侧栏）
- 新增"告警"分组。没配置时只显示一行"未配置告警"和一个"配置"按钮（渐进披露）。
- 配置项：
  - 规则多选：A1、A2、B1、C1，默认全选。
  - 通知渠道：从现有渠道里多选，至少选一个。
  - 接收人：多选平台用户。只有选了邮件渠道时才需要填。
  - "同时通知任务创建人"：只对邮件渠道生效。
  - 冷却时间：多长时间重新提醒一次，单位分钟，默认 60，0 表示不重新提醒。
  - 是否发送恢复通知：默认开启。
- 保存后立即生效。可以删除配置，删除后不再产生新告警；正在告警中的阶段会被关闭。
- 权限：能编辑任务（`CanUserEdit`）的人才能配置；能看到任务的人可以查看配置。

### R3 存储与策略中心
- 每个任务最多一条 `policy_type=sync_job` 的告警策略：
  - 新增 `task_id`、`notify_task_owner` 两列；
  - 规则写在 `conditions` 里，`metric_key` 填规则键。
- 策略中心可以按"作业告警"类型和任务筛选，列表里显示任务名。支持启用、停用、删除，编辑时打开和任务设置里一样的表单。
- 两个集群级规则加入策略中心模板，和"节点离线"一样，按集群建策略。

### R4 告警阶段
- 新增告警阶段记录，按"范围 + 集群 + 任务 + 规则"区分。同一个键同一时间最多只有一个**告警中**的阶段。
- 第一次出问题：建一个阶段，并按策略发出告警通知。
- 后续再出问题：累计次数，更新最近一次的作业和错误信息，不重复发送。
- 冷却提醒：阶段一直处于告警中，并且距离上次发送已超过策略的冷却时间，就再发一次提醒。
- 恢复：标记为已恢复，如果策略开启了恢复通知，就发一条恢复通知。
- 告警中心的确认、静默、关闭直接复用，作用于整个阶段：
  - 静默期间不发告警，也不发提醒。
  - 关闭之后，同一个键再出问题时会开一个新阶段。

### R5 告警中心
- 告警列表里能看到 sync 告警，显示：
  - 任务名、作业 ID、集群、规则名称
  - 累计次数、首次和最近一次的时间
  - 最近一次的错误（脱敏后最多 500 个字符）
  - 跳转到作业的链接
- 按集群、级别、状态筛选的效果和现有告警一致。

### R6 通知内容
- 标题：`[级别] 任务 <名称> · <规则名称>`；恢复通知用"已恢复"。
- 正文字段：
  - 集群、任务、作业 `#id`、引擎作业 ID、触发来源（手动、定时、Dolphin、CLI）
  - 累计次数、首次和最近一次的时间
  - 错误摘要
  - 链接
- 支持全部五类渠道。邮件有 HTML 版本，webhook 带结构化的 `alert` 对象。
- 链接格式是 `{app.console_url}/sync?task=<id>&job=<id>`，`console_url` 为空时不带链接。
  - 2026-10-27 实测修正：原计划用 `external_url`，但它是 Agent、Alertmanager 回调的后端地址（默认 17800），前端在 17880，拼出来的链接在 t1 上 404。因此新增可选配置 `app.console_url`。

### R7 作业深链
- 前端 `/sync` 页面支持 `?task=<id>&job=<id>`：打开对应任务，切到作业列表并选中该作业。
- 任务或作业不存在，或者没有权限时，给出提示，不报错。

### R8 不拖慢对账
- 对账、事件刷新、提交路径上报信号时**不能阻塞**：信号进入一个有界缓冲区，由后台协程处理；缓冲区满时丢弃信号并打 warning 日志。
- 不新增任何引擎调用。

### R9 CLI
- `stx sync task alert get <task-id>`
- `stx sync task alert set <task-id> --rules ... --channel <id>... --receiver <user-id>... [--notify-owner] [--cooldown 60] [--no-recovery] --confirm`
- 不提供 CLI 删除命令（`cli-guidelines.md` §11 禁止 CLI 删除资源）。CLI 用 `set <task-id> --disable --confirm` 停用告警；删除只在网页和 API 里提供。
- 现有的 `stx monitoring alert-policy` 能列出 `sync_job` 类型的策略，加一条测试覆盖。

### R10 契约登记
- 新路由登记到 `registry.go`、`route_baseline.json`，补 Swagger 注解，按 `execution-security-guidelines.md` 执行。

## Acceptance Criteria
- [ ] 任务配置了 B1、选了 webhook 渠道：作业失败时 webhook 收到一条通知，带任务名、作业 ID 和链接；再失败两次，不再新发通知，告警中心显示累计 3 次。
- [ ] 同一个任务下一次批作业成功，或者实时作业进入运行中：阶段变为已恢复，webhook 收到恢复通知。
- [ ] 任务没有配置告警：作业失败时不建阶段，也不发通知。
- [ ] `run_type=preview` 的作业失败：不触发告警。
- [ ] 引擎拒绝提交触发 A1；参数校验失败或 409 不触发。
- [ ] 提交过期触发 A2，并且不重复触发 B1。
- [ ] 停止超过截止时间触发 C1；作业最终停下后恢复。
- [ ] 冷却时间设为 1 分钟（测试里可以调短）：告警一直没恢复时会再发一次提醒；静默期间不发。
- [ ] 某个集群的 running 列表连续失败超过规则窗口：告警中心出现 D1，有集群策略时发出通知；拉取恢复后阶段变为已恢复。新集群自动带这条默认规则。
- [ ] 事件通道变为降级时触发 D2，恢复健康后阶段恢复。
- [ ] 任务设置里保存或删除告警配置立即生效；策略中心能按任务筛选出这条策略，并能编辑。
- [ ] 邮件渠道勾选"通知创建人"后，收件人里包含创建人的邮箱。
- [ ] `/sync?task=&job=` 能直接打开并选中对应作业。
- [ ] 对账时把信号缓冲区塞满，对账不阻塞，日志里有 warning。
- [ ] CLI 的 get 和 set（含 `--disable`）可用，写操作需要 `--confirm`；CLI 不提供 delete。
- [ ] 以下检查全部通过：
  - `go test ./internal/...`
  - 前端 `tsc --noEmit`、`pnpm test`
  - `check_license.py`、`check_db_compatibility.py`
  - 契约报告
- [ ] 更新 spec：新增 `backend/sync-alerts.md`，更新 `backend/index.md`；前端相关 spec 按需更新。
- [ ] t1 实测：配一个 webhook 渠道（用本机临时接收端），走完 B1、A2、C1、D1 的触发和恢复。

## Out of Scope
- 第二期的 B4 CDC 延迟告警；以后的 B5 checkpoint、B6 背压告警。
- 不做的 B2 批作业超时、B3 实时作业无数据。
- 规则级别可配置、按任务目录批量配置告警。
- 外部调度直接提交到引擎、绕过 STX 的作业（不在 STX 作业表里），见任务 `10-13-external-engine-job-visibility`。
