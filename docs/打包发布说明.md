# STX 打包发布说明

## 0. 产品版本（STX 自身）

- **权威**：git tag `vX.Y.Z`（例：`v1.0.0`）经 `release-on-tag.yml` 传入 `APP_VERSION`。
- **注入**：`package-release.sh` 用 `-ldflags -X` 写入 `internal/version`（`Version` / `GitCommit` / `BuildTime`），覆盖 stx 与 stx-agent。
- **查询**：`stx version`、`GET /api/v1/version`、`GET /api/v1/capabilities`（含 `server_version`）、控制台 About。
- **源码默认**：未注入时为 `1.0.0`；开发请勿手改 UI 硬编码版本。
- 详细设计见 [stx-self-version.md](./stx-self-version.md)。

---

## 1. 打包目标

默认 **`split` 布局**（推荐）：

- 版本资产（每次 `v*` 发版，`.github/workflows/release-on-tag.yml`）：
  - 裸二进制：`stx-linux-<arch>`、`stx-agent-linux-<arch>` + `.sha256`
  - 前端：`frontend-standalone-<ver>-linux-<arch>.tar.gz` + `.sha256`
  - `SHA256SUMS`、`install-online.sh`、`download-bundle.sh`
- deps 资产（只在 tag `deps`，手动跑 `.github/workflows/release-deps.yml`；Node / 三件套版本不变不重打）：
  - `node-<major>-<official|glibc217>-linux-<arch>.tar.gz`
  - `observability-prom…-am…-gf…-linux-<arch>.tar.gz`
  - `MANIFEST.json`

兼容：`--layout legacy` 仍可打旧式聚合 tar.gz（可选内置三件套）。

默认端口：API **17800**、前端 **17880**、gRPC **17890**。

### 1.1 产品版本（STX 自身）

- 权威来源：git tag `vX.Y.Z`（例：`v1.0.0`）→ workflow 传入 `APP_VERSION`。
- `package-release.sh` 通过 `-ldflags` 写入 `internal/version`（`Version` / `GitCommit` / `BuildTime`）；二进制内去掉 `v` 前缀。
- 查询：`stx version`、`GET /api/v1/version`（公开）、`GET /api/v1/capabilities`（CLI，含 `server_version` / `git_commit` / `build_time`）。
- 控制台 About 读 `/api/v1/version`，不再硬编码。
- 破坏 CLI 兼容时手动抬高 `internal/version.MinCLIVersion`；旧 CLI 调 capability 会 soft-warn。
- **不做** STX 产品内一键升级（仍用 `install-online.sh --version` / 重装）。详见 [stx-self-version.md](./stx-self-version.md)。

## 2. 本地打包命令

主脚本：`install/package-release.sh`

```bash
# 版本资产：裸二进制 + frontend tarball
install/package-release.sh \
  --arch all \
  --layout split \
  --build-frontend

# deps（对应 Release tag deps，不挂到版本 tag）
install/package-release.sh \
  --deps-only \
  --arch all \
  --node-major 22 \
  --node-variant official

# CentOS 7 的 Node 18 glibc217 只有 amd64，且不再重打三件套
install/package-release.sh \
  --deps-only \
  --no-observability \
  --arch amd64 \
  --node-major 18 \
  --node-variant glibc217

# 旧式聚合包（可选）
install/package-release.sh \
  --arch amd64 \
  --layout legacy \
  --bundle-observability both \
  --build-frontend
```

产物目录：`dist/releases/`

## 3. 支持的操作系统与在线 / 离线安装

### 3.0 操作系统

| 发行版 | amd64 | arm64 |
|--------|-------|-------|
| Ubuntu / Debian / Rocky / Alma / CentOS Stream / RHEL 8+ | 支持 | 支持 |
| CentOS 7（glibc 2.17，Node 走 glibc217） | 支持 | **不支持**（无 arm64 的 Node glibc217 构建） |

macOS / Windows 仅适合本地开发，不是一键安装目标。

### 3.1 在线一键

```bash
# 海外（默认 latest，默认带监控）
curl -fsSL https://github.com/LeonYoah/stx/releases/latest/download/install-online.sh | bash

# 中国（gh-proxy 已写进 URL）
curl -fsSL https://v4.gh-proxy.org/https://github.com/LeonYoah/stx/releases/latest/download/install-online.sh | bash
```

可选：`--version v0.0.1`、`--without-observability`、`STX_DOWNLOAD_MIRROR_PREFIX=https://cdn.gh-proxy.org`  
Node / 三件套默认从 Release tag `deps` 下载。

### 3.2 离线 bundle 脚本

先 `ldd --version`、`node -v`。glibc ≤ 2.17 → 组装 `node-18-glibc217`（仅 amd64）；glibc > 2.17 且本机 Node ≥ 18.18 → 不组装 Node；否则组装 `node-22-official`。

```bash
curl -fsSL https://github.com/LeonYoah/stx/releases/latest/download/download-bundle.sh | bash
```

产出 `dist/offline/stx-offline-bundle-*.tar.gz`，拷到离线机 `./install.sh --offline`。

### 3.3 手动点链接

无法跑脚本时，点 README 中的下载链接；中国把链接粘到 [https://gh-proxy.com/](https://gh-proxy.com/) 打开。文件放入 `packages/` 后 `./install.sh --offline`。Node 规则同 3.2。

### 3.4 Docker 全量（Compose）

发版资产：`stx-docker-compose.tar.gz`（`package-release` 已打包；新 tag 后可从 `latest/download` 拉）。

```bash
curl -fsSL https://github.com/LeonYoah/stx/releases/latest/download/stx-docker-compose.tar.gz | tar -xz
cd docker && cp config.example.yaml config.yaml && docker compose up -d
```

| 数据库 | Compose |
|--------|---------|
| MySQL（默认） | `docker compose up -d` |
| SQLite | `docker compose -f docker-compose.sqlite.yml up -d` |
| PostgreSQL | `docker compose -f docker-compose.postgres.yml up -d` |

单容器体验（无监控）：

```bash
# 海外
docker run -d -p 17800:17800 -p 17880:17880 -p 17890:17890 ghcr.io/leonyoah/stx-all-in-one:latest
# 中国华为云 SWR
docker run -d -p 17800:17800 -p 17880:17880 -p 17890:17890 swr.cn-east-3.myhuaweicloud.com/stx/stx-all-in-one:latest
```

### 3.5 安装后

```bash
/opt/stx/bin/start.sh
/opt/stx/bin/stop.sh
/opt/stx/bin/status.sh
# 或 systemctl restart stx
```

配置文件：`/opt/stx/config.yaml`

## 4. GitHub Actions 流程

### 4.1 main 分支 CI

工作流：`.github/workflows/ci-main.yml` — 测试与前端构建。

工作流：`.github/workflows/docker-build-check.yml` — Docker 镜像构建检查（见 [5.3](#53-本地构建镜像先打包再构建)）。

- 触发：PR / push 到 main 且改动了 `.github/docker/**`、`go.mod`、`go.sum`、`agent/go.mod`、`agent/go.sum`、`tools/stx-java-proxy/**`、`frontend/package.json`、`frontend/pnpm-lock.yaml`、`frontend/next.config.*`、`install/package-release.sh`、镜像内直接 COPY 的 `install/bin/**`、`config.example.yaml`、`scripts/stx-java-proxy.sh`，以及 `scripts/docker-*.sh`、`scripts/check-frontend-sharp-arch.sh` 或相关 workflow；只改业务代码不会触发。也可手动 `workflow_dispatch`。
- 流程：`package-release.sh` 打包产物 → 原生 runner 构建三个镜像（amd64 用 `ubuntu-latest`，arm64 用 `ubuntu-24.04-arm`，**不推送**）→ 校验镜像内文件 sha256 与产物一致 → all-in-one smoke（`/api/v1/health` 200，前端首页跟随跳转后 200）。
- 另有一个 job 在 amd64 / arm64 原生 runner 上、没有 `dist/releases/` 时构建三个镜像，确认都会失败并报出该架构缺失的文件名。
- 打包后用 `scripts/check-frontend-sharp-arch.sh` 断言每个架构的前端包只含本架构 glibc 版 sharp（`@img/sharp-linux-<cpu>` + libvips），不含其它架构 / musl / 非 linux 变体。

### 4.2 tag 发布

工作流：`.github/workflows/release-on-tag.yml`（`v*`）

- 只打包并上传 `stx`、`stx-agent`、frontend tarball
- 不同步上传 Node / 三件套
- 镜像 job 直接下载 `package-release` 的 artifact 构建，镜像里的 `stx`、agent、java-proxy jar 与前端 standalone 包和 Release 资产来自同一次编译（Dockerfile 内不再编译）
- 同步发布容器镜像到 **GHCR** 与 **华为云 SWR**：`stx-backend` / `stx-frontend` / `stx-all-in-one`
  - 需配置仓库 Secrets：`SWR_USERNAME`、`SWR_PASSWORD`（用户名形如 `cn-east-3@AK`）
  - 中国固定地址：`swr.cn-east-3.myhuaweicloud.com/stx/<镜像名>:<tag>`
  - Compose 中国用法：`STX_IMAGE_REGISTRY=swr.cn-east-3.myhuaweicloud.com/stx`（见 `deploy/docker/.env.cn.example`）

### 4.3 deps 发布

工作流：`.github/workflows/release-deps.yml`（手动 `workflow_dispatch`）

- 上传到 Release tag `deps`，且 `--latest=false`，避免抢走版本最新版
- 在线 / 离线脚本默认 `--deps-tag deps`
- Node、Prometheus、Alertmanager、Grafana 版本不变时不要重跑

## 5. Docker 说明

### 5.1 全量 Compose（推荐）

`deploy/docker/`：一份 `config.example.yaml` + `docker-compose.yml`（MySQL）/ `docker-compose.sqlite.yml` / `docker-compose.postgres.yml`。发版打成 `stx-docker-compose.tar.gz`。

```bash
cp config.example.yaml config.yaml
docker compose up -d
```

### 5.2 all-in-one 单镜像

`stx-all-in-one` 含后端、前端、镜像内 Node，**不含**监控三件套。全量监控请用 Compose。

```bash
docker run -d -p 17800:17800 -p 17880:17880 -p 17890:17890 \
  ghcr.io/leonyoah/stx-all-in-one:latest
# 中国：swr.cn-east-3.myhuaweicloud.com/stx/stx-all-in-one:latest
```

入口脚本：`.github/docker/all-in-one-entrypoint.sh`

### 5.3 本地构建镜像（先打包再构建）

`.github/docker/Dockerfile.backend`、`Dockerfile.frontend`、`Dockerfile.all-in-one` **只消费** `dist/releases/` 中的发版产物，不在 Docker 里编译 Go、Java 或前端。缺任何产物会直接构建失败，并列出缺失的文件名。

| 镜像 | 需要的产物（`dist/releases/`） |
|------|------|
| `stx-backend` | `stx-linux-<arch>`、`stx-agent-linux-amd64`、`stx-agent-linux-arm64`、`stx-java-proxy-v2.jar`、`stx-java-proxy-v3.jar` |
| `stx-frontend` | `frontend-standalone-linux-<arch>.tar.gz` |
| `stx-all-in-one` | 以上全部 |

依赖：Go、Maven + JDK 11、curl、python3（与 `install/package-release.sh` 一致），以及 Docker Buildx。

```bash
# 一条命令：打包产物 + 构建当前架构的三个镜像 + 校验镜像内 sha256 与产物一致
make docker-images
# 等价于：scripts/docker-build-images.sh --verify

# 已有 dist/releases/ 时只重建镜像，并对 all-in-one 跑 smoke
make docker-smoke

# 指定架构 / 镜像（非本机架构需要 QEMU：docker run --privileged --rm tonistiigi/binfmt --install arm64）
make docker-images DOCKER_PLATFORMS=linux/amd64,linux/arm64 DOCKER_IMAGES=all-in-one
```

也可以手动分两步：

```bash
install/package-release.sh --arch all --layout split --build-frontend
docker buildx build --platform linux/amd64 -f .github/docker/Dockerfile.all-in-one -t stx-all-in-one:local-amd64 --load .
scripts/docker-verify-release-artifacts.sh stx-all-in-one:local-amd64 all-in-one amd64
scripts/docker-smoke-all-in-one.sh stx-all-in-one:local-amd64
```

前端只在宿主机构建一次（同一份 Next.js 输出），但按架构分别打包：`package-release.sh` 构建前端时临时写入 `frontend/pnpm-workspace.yaml`（`supportedArchitectures`，构建后删除），让 pnpm 同时装上 x64 与 arm64 的 sharp；打包时再按架构裁剪，`frontend-standalone-linux-amd64.tar.gz` 只保留 `@img/sharp-linux-x64` + `@img/sharp-libvips-linux-x64`，`-arm64.tar.gz` 只保留 `@img/sharp-linux-arm64` + `@img/sharp-libvips-linux-arm64`（不含 musl 与其它架构）。`stx-upgrade-*-linux-<arch>` 自升级包与 legacy 包里的前端也使用对应架构的裁剪结果。两个 tarball 除 sharp 原生包外内容一致，安装脚本本来就按 `linux-${ARCH}` 选包，无需改动。缺少本架构 sharp 时 `--build-frontend` 打包直接失败。（#57 扩展范围，已经 Trey 确认。）

镜像标签为 `stx-<镜像>:<tag>-<arch>`（默认 `local`）。每个 Dockerfile 旁边的 `Dockerfile.*.dockerignore` 是白名单，只把需要的产物和脚本送进构建上下文。
