# STX 内置监控说明

STX 自带监控：指标采集、存储、查询、趋势图和指标告警都在 STX 后端进程里完成，**不需要另外安装或维护任何监控组件**。
首页大盘、集群 / 作业趋势、作业详情的「趋势」页签、诊断报告里的指标快照和策略中心的指标告警都用这份数据。

## 采集什么

| 来源 | 内容 | 方式 |
| --- | --- | --- |
| SeaTunnel 引擎 | 每个受管集群的每个在线节点的引擎指标（JVM 堆 / 非堆、GC、线程、CPU、FD、作业线程池、Hazelcast 分区与执行器、作业状态计数等） | 后端按 `scrape_interval`（默认 15 秒）访问节点的 `seatunnel_metrics.path`（默认 `/hazelcast/rest/instance/metrics`），不需要在节点上装任何东西 |
| STX 作业 | 每个作业的读写条数 / 字节、提交条数、CDC 延迟、Checkpoint 耗时与失败次数、算子忙碌度、边背压、表级读写量 | 后端在作业状态对账时直接写入，作业结束时写入最终值后停止 |

节点不可达时，该节点在可用性图上显示为不可用，策略中心「引擎指标采集」能力卡给出原因。

## 配置

`config.yaml` 的 `observability` 段（默认值见 `config.example.yaml`）：

```yaml
observability:
  enabled: true              # 总开关，默认开启
  storage:
    dir: "data/tsdb"         # 数据目录，相对安装目录
    retention: "31d"         # 保留时长，支持 s/m/h/d/w/y
    max_size: 32212254720    # 存储上限（字节），默认 30GiB；显式写 0 表示不限
  scrape_interval: "15s"     # 引擎指标采集间隔
  eval_interval: "15s"       # 指标告警评估间隔
  query_timeout: "8s"        # 单次查询超时
  max_samples: 10000000      # 单次查询最多加载的样本数（约 160MB）
  sample_limit: 50000        # 每个抓取目标单轮样本上限；超限丢弃该目标本轮
  seatunnel_metrics:
    path: "/hazelcast/rest/instance/metrics"
    probe_timeout_seconds: 2
```

修改后重启 STX 生效。

### 保留时长与磁盘

- 数据按 `retention` 与 `max_size` 两个条件删除，先到哪个按哪个。默认能看最近 31 天，首页「每日 / 每月读写量」也受此限制。
- 想看更久的历史，同时调大 `retention` 和 `max_size`。
- 占用大致与「节点数 × 引擎指标数 + 作业数」成正比，几十个节点的规模通常在几 GB 以内。
- 内嵌 tsdb 自己的 `prometheus_tsdb_*` / `prometheus_engine_*` 以及 STX 进程的 `go_*` / `process_*` 会以 `job="stx_embedded"` 写回同一存储，可用 `stx monitoring integration status` 看 `embedded_tsdb.meta`（head 序列、块字节、compaction 失败次数）。
- 每个抓取目标单轮超过 `sample_limit`（默认 5 万样本）时，只丢弃该目标本轮并在状态接口记 `last_error`，不影响其他节点。建议活跃序列不超过 2 万；详见 `.trellis/spec/backend/embedded-tsdb-capacity.md`。
- 容量数字分两档：突发写入（`go test` 三档序列）和实时长时间运行。后者按 15s 抓取至少跑 48h：`./scripts/tsdb-soak.sh`（输出 `tmp/tsdb-soak-48h.jsonl`）。突发档不能代替 48h soak。

### 关闭

`enabled: false`（或安装时加 `--without-observability`）后：不再采集与评估，趋势图显示「内置监控未开启」，
指标类告警策略不可用；集群卡片、节点表、作业列表、运行日历、平台健康告警和作业告警不受影响。

## 告警

- **内置规则**：引擎指标端点不可达、节点状态异常、分区不安全、作业线程池积压 / 拒绝、JVM 堆、进程 CPU、GC 耗时、FD 使用率、线程死锁等，
  开箱即用，触发后进入告警中心并按通知路由投递。
- **指标模板策略**：在策略中心选择 CPU、内存、FD、失败作业等模板，只需设置阈值、窗口与通知渠道。
- 告警的去重、冷却重发、静默、恢复通知与平台健康告警一致；STX 重启后，处于「持续中」计时的告警会继续计时，不会从头开始。

### 告警类别与术语

- 告警中心按**告警类别**（`source_type`）过滤，取值为 `platform_health`（平台健康）、`metric`（指标告警）、`job`（作业告警）。
  类别按**规则归属**判定：集群级的作业健康规则（如作业状态获取失败、事件通道降级）属于平台健康，任务级作业规则（如作业运行失败、CDC 延迟过高）属于作业告警。
- `source_type` 只表达类别，不代表存储来源：本地进程事件、sync 阶段、指标序列是内部存储种类，仅内部使用；
  需要区分 sync 阶段时按 `alert_id` 的 `sync:` 前缀判断（例如阶段专属的发生次数、自动关闭原因展示）。
- 术语约定：策略中心里管理的是**告警策略**（AlertPolicy），按集群配置开关 / 阈值 / 窗口的是**检测规则**（AlertRule）。
- 通知路由的 `source_type` 过滤同样取这三个类别值；巡检自动策略的「告警触发」条件从 `GET /api/v1/monitoring/alert-rules/catalog` 选择规则键精确匹配，可叠加「至少 N 个对象同时触发」与「至少持续 N 分钟」。

## 从旧版本升级

旧版本通过外部的 Prometheus / Alertmanager / Grafana 提供监控。升级到内置监控有两种方式，后续行为不同：

### `install.sh` 重装升级

重新运行 `install-online.sh`（同目录覆盖安装）会用**当前安装脚本**直接写入新的 `bin/` 全套脚本，不经过旧升级器，升级后不需要任何布局修复。
旧的 `observability/` 目录和数据**保留不删**，确认不需要后可手动删除。

### 应用内一键升级（界面 / API / CLI）

一键升级由**旧版本升级器**执行，它只替换 `stx` 二进制、`lib/`、`scripts/` 和 `frontend/`，**不会替换 `bin/`**。
因此修复动作放在新二进制启动流程里，首次启动时自动完成：

- **安装布局自修复**：检测到安装目录布局时，用内嵌的新脚本覆盖 `bin/start.sh` / `bin/stop.sh` / `bin/status.sh`
  （旧文件备份为 `bin/<名>.bak-<UTC 时间戳>`），并把 `bin/lib/observability.sh` 移走为 `.bak-<时间戳>`；幂等，第二次启动不再重复。
- **旧三件套收尾**：启动后约 3 分钟窗口内按 `observability/*/*.pid` 文件逐个停止仍在运行的 Prometheus /
  Alertmanager / Grafana（发信号前用 `/proc/<pid>/exe` 核对进程身份，pid 被复用时只清理 pid 文件）。
  `observability/` 数据目录保留不删。
- **遗留告警收尾**：外部 Alertmanager 时代产生、从未恢复的告警会被一次性标记为已恢复，不发送恢复通知。
- **失效配置提示**：旧告警类别（`local_process_event` / `remote_alertmanager` / `sync`）的通知路由、
  旧条件（`PROM_*` / `NODE_UNHEALTHY`、未选规则的 `ALERT_FIRING`）的自动巡检策略不再生效但不会被删除；
  列表 / 详情 API、CLI 与诊断面板会通过 `invalid_reason` 标出，需编辑重新选择。

升级后 `bin/start.sh` 不再启动任何外部监控组件；如果还在用旧 systemd 单元，其传入的 `--observability`
参数会被接受并忽略。

### 删除的接口

以下接口已随外部监控栈移除，调用方会收到 404：

- `GET /monitoring/prometheus/discovery`
- `GET /monitoring/prometheus/jobs/metrics`
- `POST /monitoring/alertmanager/webhook`（外部 Alertmanager 推送端点，请停止推送）
- `ANY /monitoring/proxy/grafana`
- `ANY /monitoring/proxy/grafana/*proxyPath`

STX 对外推送告警通知的 webhook / 飞书 / 企业微信 / 钉钉 / 邮件渠道不受影响。

### 其他升级注意事项

- 内置监控**默认开启**：默认保存 31 天、上限 30 GiB（`observability.retention` / `max_size`）。
- 内存 / 磁盘占用相比旧三件套整体下降，但新增了内置 tsdb 的常驻开销：小内存机器（< 2 GiB）建议安装时加
  `--without-observability` 关闭内置监控，或调低 `retention` / `max_size`。
- **时区变化**：引擎时间回退从「展示时区」改为控制面机器时区（`time.Local`）。升级前建议把各 Agent
  所在机器的时区与控制面对齐；容器部署建议显式设置 `TZ` 或 `STX_SEATUNNEL_TIMEZONE`。
- **Agent**：老版本 Agent 继续兼容，但主机指标采集与节点时区上报需要把 Agent 升级到当前版本才会完整工作。
- 旧配置文件里的 `observability.prometheus` / `alertmanager` / `grafana` / `remote_ingest` 段会被忽略，
  不影响启动，加载时记一条 WARN 提示清理。
- 旧的安装参数（`--with-observability`、`--prometheus-port`、`--alertmanager-port`、`--grafana-port`）
  不再被接受，传入会报 unknown option，请从安装命令里移除。
- **Docker Compose**：升级到只剩 STX 前后端与数据库容器后，用 `docker compose up -d --remove-orphans`
  移除遗留的 Prometheus / Alertmanager / Grafana 容器；监控数据在 `data/stx/tsdb`。
- 历史监控数据不自动迁移，升级后从零开始积累。若必须查看旧数据，可把 `storage.dir` 临时指向旧的
  Prometheus 数据目录（同为同一存储格式）。

## 常见问题

**趋势图显示「监控数据暂不可用」**：数据目录无法打开（权限、磁盘满）或查询超时。查看 `logs/backend.log` 中 `[Observability]` 开头的日志。

**某个节点的图是空的**：确认节点在线、配置了 Hazelcast 端口，且 STX 能访问 `http://<节点 IP>:<Hazelcast 端口><seatunnel_metrics.path>`。

**作业趋势没有数据**：作业趋势来自作业状态对账，作业需要处于运行中；已结束的作业可以在作业详情里按「作业全程」查看历史。
